## 摘要

TBG Phase R02 的 9 个 task（T1–T9）分散在 7 个独立会话中执行，每个会话从零上下文开始，靠读磁盘重建执行现场。逐条解析会话日志后得到三个结论：

1. **新会话需要四类信息**：契约（做什么）、事实（世界是什么样）、状态（现在在哪、哪些结论失效）、资产（操作对象在哪），彼此构成有向图（契约是根，状态是覆盖层，事实描述资产）。
2. **信息有两种获取代价**：读答案（读内联摘要，推理≈0）与读线索+推理（读源文件 + 从线索推出结论）。二者的差异才是 `d_i ≫ s_i` 的根源——内联省的主要不是读入量，而是"线索→答案"的推理。
3. **优化目标 = 总获取 token 最小**：`min(s_i, d_i)` 每事实每会话，叠加复用 `min(w_i + f_i·s_i, f_i·d_i)`。R02 实证：纯推导税（重发现）从 T6 的 24k 降到 T9 的 4.8k（HANDOFF 砍 5 倍），`plan.md`/`log.md` 全量重读是最大可省浪费（~10k/会话）。

方案：分层 SSOT（契约→tasks、事实→KNOWN、状态→STATUS/HANDOFF、资产→路径、操作规则→skill）+ 按需指针读 + `(s,d,f)` 三元组分路。

**R02 试点追记（2026-09-15）**：方案落地为 `context_handoff_protocol.md` 后在 R02 Stage 3（T10–T19）试点。机制本身成立——「重复侦查已确立事实」的税被定向消灭（带干净 HANDOFF 的任务 plan+log 读入降到 0.9–4.8k）、结论有效性状态机全程无事故、0 次委托人中止；但 §4.6 四指标中「总读入 ≤50k」未达标，并暴露 8 个新问题（按重要性：s_i 非恒定、executor 做 planning、依赖图 DAG 残缺、fork 重复读、读规则未执行、依赖值时间错位、自续接冗余、指标口径失效），修正与后续见 §5。

## 1. 模型：新对话需要什么信息、怎么获取

### 1.1 公理

一个新对话 = 一个**零内存、只可读磁盘的执行进程**。它执行 task T 所需的最小信息 = 「执行 T 的全部状态」−「能从环境（文件/代码/运行结果）自己重推的部分」。故交接要传的是**不可推导信息**，可推导信息只需**指针**。但指针不是免费的——跟随指针每次都要付「读源 + 推理」，所以真正的最小化对象是**总获取成本**，不是"传入量"（见 §3）。

### 1.2 四类信息 + 关系（有向图）

按"对执行的必要性 × 可推导性 × 变化速率"分类；"规则"不单列——任务级规则是契约的约束/分工条款，通用协议是 skill/系统指令（零 token）：

| 类 | 回答的问题 | 可推导？ | 变化速率 | 落点 |
|---|---|---|---|---|
| ① **契约** Contract | 做什么 / 做成什么样 / 不能做什么 | ❌ 人类意图 | 任务级一次 | tasks.md（**根节点**）|
| ② **事实** Facts | 世界是什么样（语义/结构/结论+有效性/环境）| △ 可推导但贵，有的不可重推 | 两档：不变(项目级)/沉淀(phase级) | CONTEXT + KNOWN |
| ③ **状态** State | 现在在哪 / 哪些结论已失效 | △ 可读 checkbox 但需快照防歧义 | 逐任务变 | STATUS + HANDOFF |
| ④ **资产** Assets | 操作对象在哪 | ❌ 人造产物，只能被指向 | 随任务增删 | 文件本体，doc 只存路径 |

```
契约(根) ──输入/输出(资产路径)──▶ 资产
   │──背景/父计划(§锚)──▶ 事实
   │──约束/分工(内嵌)──▶ 规则
状态 ──进度──▶ 契约    （走到第几步）
状态 ──有效性──▶ 事实  （哪些结论已撤回/取代）  ← 结论有效性状态机
事实 ──描述──▶ 资产    （data 的原子数/md5）
```

- **契约是唯一必须主动传入的节点**（人类意图不可推导），且它自带的"输入/背景/约束"就是导航页 = 根节点 + 全部出边。
- **状态是唯一的覆盖层**，不新增事实，只标记"契约走到哪、哪些事实失效"。**结论有效性状态机**（如 T9 的"T6 结论有效 / T7/T8 收敛结论已撤回"）是状态类里最有价值的一半。
- **事实与资产是被指向的叶子**，惰性拉取。

### 1.3 获取方式三路（读取 vs 推理的精确化）

"读取 vs 推理"不是二元——读取本身要拆成两类，只有"读线索"才触发推理：

| 获取方式 | 读后是否还要推理 | 例 |
|---|---|---|
| **读答案** | ❌ 读入即用 | 内联结论"盒子换算 xhi=xhi_bound−xy=1284.645" |
| **读线索 + 推理** | ✅ 读了要**转化**成答案 | 读 dump 头/源码/ssh 探测输出，再自己推出结论 |
| **读垃圾 + 过滤** | ✅ 读了要**过滤** | plan.md 全量里 95% 无关段落 |

推理成本 ≈ 线索 × 转化率 + 垃圾 × 过滤率；读答案几乎不贡献推理。这是 §3 `d_i ≫ s_i` 的根源：`s_i`=读答案（读入≈使用），`d_i`=读线索+推理。

### 1.4 task 类型 → 信息需求

| 类型 | 实例 | 最小交接集 | 是否需 HANDOFF |
|---|---|---|---|
| **A 纯本地盘点/文档** | T1 | tasks + 输入指针 + 目标 KNOWN 骨架 | ❌ |
| **B 本地数据/脚本/可视化** | T2、T5 | tasks + 上游产物路径 + KNOWN 数据格式指针 | ⚠️ 可省，但必须给"格式见 KNOWN §x"指针 |
| **C 集群计算**（最重）| T3/T4、T6/T7/T8 | tasks + 结构约定 + 集群 runbook + 资产清单(双路径) + 作业清单 + 续接动作 + 风险预案 + 已改代码 provenance | ✅ **必写**（推送后即写）|
| **D 修正/补证据** | T9 | tasks + **结论有效性状态机** + 分工铁律 + 待拍板点 | ✅ 必写 |

### 1.5 生命周期分层（决定"放哪"）

| 档 | 内容 | 变化 | 落点 |
|---|---|---|---|
| 不变 | 架构/约定/参数语义/数据格式 | 跨 phase 稳定 | CONTEXT（项目级）+ 共享知识(L2) |
| 沉淀 | phase 内已确立事实/结论/runbook | 逐任务增长 | KNOWN（phase 级 SSOT）|
| 现场 | 进度/阻塞/最近决策/作业状态 | 逐任务变 | STATUS + HANDOFF |
| 瞬态 | 作业清单/续接点/隧道状态 | 消费一次即失效 | HANDOFF（归档后消失）|

## 2. 实证：R02 七个会话读了什么、花了多少

### 2.1 测量口径

- 数据：7 个 jsonl 的 `tool/result` 内容（`read`/`grep`/`glob`/`bash`/`read_image`/`skill` 返回文本），**不含**模型自身 reasoning 与输出。
- token 估算：jsonl 无逐条 token 记录，用字符启发式 `中文≈1 token/字、ASCII≈1 token/4 字符`。绝对值是量级估算（±30%），**比值与趋势稳健**。
- 四分类口径：
  - **传入** = 读文档层 .md（tasks/CONTEXT/STATUS/KNOWN/plan/HANDOFF/REVIEW/log/REPORT/README）+ skill 加载。
  - **重发现** = bash 侦察命令（which/ls/find/head/cat/grep/md5/wc/sed/env/date/pwd/ssh 探测/sacct/squeue/conda 等）——纯推导税。
  - **源码读取** = read/grep/read_image 非 .md 文件（src/config/slurm/data/reference/tools）——工作面，部分混入重推。
  - **执行+产出** = bash 执行（python/lmp/sbatch/scp/cp/mv）+ write/edit + 编排。

### 2.2 开机读序列

7 个会话统一"开机五件套"：`tasks → CONTEXT → STATUS → KNOWN(+plan 节选)`，外加任务专属资产。差异：

| 会话 | 特征 | 有无 HANDOFF |
|---|---|---|
| T1_T2 | 首任务：`glob` 定位 + 全量读 plan + 盘点 reference/data | ❌（从头建 KNOWN）|
| T3_T4 | `pwd && ls -la`(冗余) + skill cluster-workflow + 读 dump_to_data.py | ❌（是 HANDOFF_T4 生产者）|
| T5 | 无 HANDOFF，step21 重读 dump_to_data.py 重推格式 | ❌ |
| T6_T7_T8 | **~80 条 ssh** 重探 module/mpirun | ❌（HANDOFF_T6/T7 生产者）|
| T9 | 开机第 2 读 = **HANDOFF_T9** + REPORT_T6/7/8 → 直通执行 | ✅ 唯一真跨天消费者 |

### 2.3 token 定量

| 会话 | 传入 | 重发现 | 源码读取 | 执行+产出 | 总读入 |
|---|---:|---:|---:|---:|---:|
| session(审计) | 57.3k | 14.7k | 2.4k | 30.2k | 104.7k |
| plan_task | 34.2k | 12.8k | 26.1k | 1.6k | 74.7k |
| T1_T2 | 22.6k | 5.0k | 3.1k | 4.5k | 35.1k |
| T3_T4 | 27.2k | 7.4k | 4.0k | 17.1k | 55.7k |
| T5 | 35.4k | 7.9k | **23.1k** | 6.3k | 72.6k |
| T6_T7_T8 | 43.8k | **24.3k** | 27.1k | 10.2k | 105.4k |
| T9 | 28.1k | **4.8k** | 26.2k | 10.0k | 69.1k |

三个发现：

1. **传入绝对量稳定 ~22–44k，但结构有浪费**。`plan.md` 是最大单项（7.8–8.5k/次，按 § 只需 ~1.5k），`log.md` 全量 4–4.3k（最新 1–2 条只需 ~1k）。
2. **纯推导税（重发现）随交接成熟度波动 5 倍**：T6 24.3k（80 条 ssh 重探）→ T9 4.8k（HANDOFF 指引）。这是"交接差"最直接的读数。
3. **源码读取 20–27k 是工作地板**（读 io_vis.py 函数 API 是作图工作本身），但 T5 的 23k 里混入了重读 dump_to_data.py 重推 KNOWN 已有格式（可省的税）。

推理（reasoning）另计：T1 40k / T3_T4 94k / T5 114k / T6_T7_T8 230k / T9 43k——读得多(线索/垃圾)会放大推理，但"读入省 1 token → 推理省 2–5 token"是未证实的假说（T6 vs T9 的推理差混入了任务数差异）。

### 2.4 有效 vs 无效

| 读 | 判定 | 依据 |
|---|---|---|
| tasks.md | ✅ 有效 | 契约根节点，7 会话全部首读 |
| KNOWN.md | ✅ 有效 | SSOT 事实库，消除重发现（§1.6 结构/§2 结论/§3 runbook）|
| HANDOFF(存在时) | ✅ 有效 | 瞬态快照，T9 证明直通执行 |
| STATUS.md | ✅ 有效 | 动态进度+结论有效性 |
| 任务专属资产 | ✅ 有效 | 工作面 |
| `pwd && ls -la` / `glob` 定位 | ❌ 冗余 | cwd 已在 runtime context；路径稳定 |
| 全量读 plan/log | ❌ 冗余 | 95% 与本任务无关，应按 § 指针/最新 N 条 |
| 每会话 which python+conda | ❌ 冗余 | 环境已固化，用固定 activate |
| 重推 KNOWN 已有事实 | ❌ 税 | SSOT 未命中（T5 重读 dump_to_data.py）|
| ~80 条 ssh 重探 | ❌ 税 | 上游未提前写 runbook（事后晋升 KNOWN §3）|

## 3. 优化目标与函数

### 3.1 每事实每会话：两条互斥路径取 min

消费者获取一个事实只有两条**互斥**路径（不是相加）：

$$\min\left(\underbrace{s_i}_{\text{读答案(内联)}},\ \underbrace{r_{src}+\text{reason}}_{= d_i,\ \text{读线索}+\text{重推}}\right)$$

- 内联 → 读答案（读一行摘要，推理≈0）
- 指针/重推 → 读线索 + 重推（读源文件 + 从线索推出结论）

`d_i = r_{src} + \text{reason}`，`s_i` 与 `d_i` 是同一维度（消费者读）的两种取值。

### 3.2 生命周期 + 复用

加入生产者一次性写成本 `w_i` 与未来消费频率 `f_i`：

$$\min\left(w_i + f_i\cdot s_i,\quad f_i\cdot d_i\right)$$

- 内联腿：写一次 `w_i` + `f_i` 次读答案
- 重推腿：`f_i` 次读线索+重推

`f_i` 是放大器：内联节省 ≈ `f_i(d_i - s_i) - w_i`。**复用问题的本质**：把"每会话重推 `d_i`"换成"写一次 `w_i` + 每会话读 `s_i`"，当 `f_i ≥ 2` 且 `d_i ≫ s_i` 时省最多。

### 3.3 三元组 `(s_i, d_i, f_i)` 判据

| 条件 | 策略 | 例 |
|---|---|---|
| `d_i ≫ s_i`（难推导且能压成一行）| **内联进 SSOT** | 盒子换算、md5、mpirun 修复 |
| `d_i ≈ s_i` 且无法短摘要（长文件）| **指针** | io_vis.py 函数体、plan.md 全文 |
| `d_i < s_i`（易推导 / 只用一次）| **重推，不存** | `which python`、瞬时作业状态 |

"晋升 KNOWN"的判据不是"重不重要"，而是**"会不会被 ≥2 个未来对话用到，且重推成本 > 内联成本"**。

## 4. 方案：交接的落法

### 4.1 分层存储（按 §1.5 生命周期 + §1.2 类型）

| 信息 | 落点 | 规则 |
|---|---|---|
| 契约 | tasks.md | 根节点，自包含导航（输入=路径/背景=§锚/约束=分工）|
| 事实（不变）| CONTEXT + 共享知识 | 冷启动全量，暖会话按 § |
| 事实（沉淀）| KNOWN | 每条"一句话结论打头"，§ 锚可寻址 |
| 状态 | STATUS + HANDOFF | STATUS 三行式；HANDOFF 瘦身 ~1.5–2k |
| 资产 | 文件本体 | doc 只存路径，不复制内容 |
| 操作规则（通用）| skill | 可执行操作固化到 skill，项目内只留指针 |

### 4.2 读规则（run-task「收集上下文」按需指针化）

```
0. CONTEXT.md          ← 冷启动全量；暖会话按 § 读架构/参数/约定，已被覆盖则跳过
1. tasks.md            ← 契约根，读全文
2. HANDOFF_{task}.md   ← 若存在：瞬态快照
3. KNOWN.md            ← 按 tasks/HANDOFF 的 § 指针 grep，命中即止
4. STATUS.md           ← 只读「当前阶段/下一步/阻塞」三节
5. 任务专属资产         ← 按需
6. plan §（按指针）    ← 只读「父计划」指向的小节，不整份
```

删除项：`pwd && ls -la`、`glob` 定位、全量 plan/log、每会话环境探测、重推 KNOWN 已有事实。

### 4.3 写规则

1. **一句话结论打头**：KNOWN 每条事实先给结论再给依据，grep 命中即得。
2. **即时晋升**：新踩的坑在**同一 turn** 内晋升 KNOWN/runbook，不等下次会话（T6 的 mpirun 直到第 4 次消费才晋升，前三次 `K×d_i` 白付）。
3. **HANDOFF 瘦身**：只放"续接点 + 作业清单 + 勿重算输入指针 + 环境探测清单"，持久事实晋升 KNOWN 不滞留。
4. **事实/建议分层**：runbook 条目拆「事实（观测）+ 建议【适用范围】」，避免打包（case 06）。

### 4.4 SKILL 修改

| skill | 变更 |
|---|---|
| `run-task` | 「收集上下文」节改为 §4.2 的按需读序 |
| `handoff-template` | 加「环境探测清单」节 + 明确"只放指针不放内容" |
| `create-task` | 「输入」字段强制带格式/来源指针（`格式见 KNOWN §x`）|

> 集群类操作规则已固化进 `cluster-workflow` skill（R02 陷阱条目 + 事实/建议分层），本项目 KNOWN §3 相应改为指针，此处不重复。

### 4.5 反模式（怎么写错）

1. **三层同记**：同一事实同时存在于 skill + KNOWN + HANDOFF，措辞还略有差异 → SSOT 违反，应单归属 + 他处指针。
2. **事实/建议打包**：runbook 条目"事实 + 建议"合成一句 → 版本一改，读者分不清哪半句仍成立（case 06 等增益缺陷）。
3. **全量读 plan/log**：几百行里 95% 无关，token 纯浪费。
4. **动态进度混入 KNOWN/快照**：快照语义与持久语义混淆，进度应进 STATUS。
5. **"当前值"不标时效**：隧道/队列/缓存等易过期状态，下一会话误当永久事实。
6. **集群推送后不写 HANDOFF**：集群状态若靠内存续接，会话一死全丢。

### 5.3 出现的新问题（按重要性排序）

> 排序准则：根因深度 × 影响面（token/错误）× 一般性（超出 R02 的程度）。

1. **「s_i 内联摘要恒定」假设失效（模型级）**。§3 的 `min(w_i+f_i·s_i, f_i·d_i)` 把内联摘要成本 s_i 当常数；试点中 KNOWN/plan/tasks/log 在 phase 内长到 45/44/61/72KB，全文读代价随知识累积而涨（T19 一次 KNOWN 全文读 ≈11k token）。**SSOT 削减「重复读」，但削不掉「知识累积」**——除非严格用 § 指针 grep 把读入钉在命中段落，s_i 随项目增长持续放大。这是 §3 模型的假设缺口。
2. **executor 做 planning 的反模式（架构级）**。plan 修订混在执行会话里做（人类在 T9/T13 执行会话下「按这个方案修改 plan 和 task」），执行会话为重建规划状态付 plan+log 重读 ≈98k（T17 读 log ×7 = 29.9k 即实例）。「事实晋升」executor 可热写，「结构修订」必须回 planning——引出人类/planning/execution 三角色与 executor→planner 反馈通道（见 §5.4）。
3. **依赖图是 DAG 且残缺（契约级）**。依赖不是链：T14 实际依赖 5 个生产者（T13 峰位 + T12 参数 + T17 E_F + T18 d + T15 ξ，含编号更大的交叉边），tasks「输入」只写 2 项；编号、执行序、依赖序三者不一致。契约残缺时执行者被迫自行重建依赖（T17 读 log ×7 = 29.9k）。
4. **fork 分支重复读（金额最大）**。T13/T14/T17/T18 各产生 sub/PLL 平行分支，各自重读同一份上下文 ≈522k。§1.2 模型默认串行执行，未覆盖 fork；修复依赖消费者组装视图（每个 fork 只读 1–2k）。
5. **读规则未被稳定执行（直接、但属下游症状）**。协议 §2「KNOWN 按 § 指针 grep、命中即止」整个 Stage 3 只被 T15 偶然遵守一次（`grep KNOWN "2\.7|衰减|ξ"`），其余全部全文 read（最干净的 T19 仍 read KNOWN ×2）。若 §5.4 的消费者组装落地，执行者根本不需要读 KNOWN，此问题自然消失——故列在 P3/P4 之后。
6. **依赖值的时间错位（概念级）**。依赖值（m=8）是生产者的**输出**，planning 时不存在；「写进 task 条目」与「新对话开头先写清单再执行」都是错的时间点（后者信息一点没少读、还多写一份）。正解：依赖**图**进 tasks（planning 时可知），依赖**值**由生产者收尾热写 KNOWN 一句话、消费者组装时拉取。
7. **自续接 HANDOFF 冗余（局部）**。R02 的 HANDOFF_Tn 多为「推完作业写给自己」，但 10 个续接点全部发生在同一 durable 会话（续接 turn 首动作 `sacct -j` 的 ID 来自上下文，从不读 HANDOFF_Tn），与同刻必写的 log 推送条目 ~80% 重复（两层同记）。协议 §5.6 把「必须落盘续接载荷」与「载体必须是 HANDOFF 文件」错误捆绑——载荷并入 log 结构化推送条目；独立文件只在 `P(会话死亡)×重建成本 > 写快照成本` 时才写。
8. **「总读入 ≤50k」指标口径失效（度量级）**。Stage 3 是 40 作业扫描+出图，Stage 1/2 是 8 作业筛选，「总读入」非同类比。需按任务类型（A/B/C/D）分型设目标，并以「HANDOFF ≤2k 且自包含 + 执行会话零 KNOWN 全文读」取代一刀切。

## 摘要

**本文的主旨是"通则"，插件只是验证通则的一个实例。**

从控制论与系统工程出发，软件设计可以被归结为九条基本原则，分属三个视角：**控制论**（regulation）讲"程序如何按愿望运行"，**信息**（communication）讲"模块之间如何约定与隔离"，**系统工程**（design）讲"如何把零件变成靠谱的整体"。这些原则的每一句都先给出纯软件设计的陈述与物理解释，**不依赖任何具体项目**。

随后，以自研的 DSH 插件 `dsh-notify`（任务完成时经 WSL→Windows 弹 toast）作为落地实例，分两个层次说明原则如何被体现：

- **层次一 · 产品内（控制论）**：插件本身被设计成一个旁路反馈控制器——传感器=宿主发布的 `agent/status` 事件、控制器=纯函数状态机、执行器=跨 OS 的 toast 发送器；
- **层次二 · 过程层（系统工程）**：编写与维护这个插件的**项目过程**，本身跑了一遍系统工程 V 模型（需求/非目标 → 钩子核实 → 功能分解 → 实现 → V&V → 维护）。

两层之间是**生成关系**：过程（层二）的每一个动作，都在产物（层一）里"长出"对应的结构。文末给出这条因果链，作为把"通则"翻译成"工程动作"的抓手。

**第三部分（§11–§16）** 是插件真机验证通过后的**事后复盘**：记录实际执行与设计意图之间的偏差、暴露的失效模式（含新增 F7「执行器假成功」）与教训。

# 第一部分（主）：软件开发的基本原则

> **新手读法**：下面每条原则按固定结构展开——**①一句话直觉 → ②控制论概念 → ③反例/正例代码 → ④物理解释 → ⑤自查**。代码用 JavaScript 写（与你正在写的插件同语言），但刻意**不涉及任何具体项目**，是通用示例。你可以先只读"直觉"和"反例/正例"，概念与物理解释留到需要追根究底时再看。

## 1. 总纲：程序 = 反馈控制器

控制论研究"一个系统如何通过**感知 → 比较 → 调整**的循环维持目标状态"；系统工程研究"如何设计一个由多部分组成的整体"。把这两句话合起来，就是软件设计的统一视角：

> **一段程序不是一条"从头跑到尾的指令流水线"，而是一个（或几个）反馈回路的某个片段。**

任何软件单元都可以问三个问题：

1. 它**感知**什么？（输入 / 事件 / 传感器）
2. 它**比较**什么？（与目标、与历史状态的差异）
3. 它**调整**什么？（输出 / 动作 / 执行器）

缺了"比较"，就只是一个开环的反应式脚本；有了"比较 + 记忆"，才是一个闭环控制器。

**先看一个最朴素的完整例子**——恒温器，它是控制论的最小系统，也几乎是所有软件的隐喻：

```js
// 恒温器 = 最小的反馈控制器
const target = 25                      // 设定值（我要什么）
let current = 20                       // 状态（现在是什么）

function tick(sensorReading) {         // 感知：读传感器
  current = sensorReading
  const error = target - current       // 比较：误差 = 目标 - 现状
  if (error > 0) heater.on()           // 调整：按误差方向动作
  else heater.off()
}
```

记住这五行代码的结构——**设定值、状态、感知、比较、调整**——下面九条原则全是从这五行里长出来的。

## 2. 控制论视角（regulation）— 让程序按愿望运行

### 原则 ① 闭环优于开环（Closed Loop over Open Loop）

- **一句话直觉**：不要"来了就干"，要"先判断再干"。

- **控制论概念**：开环 $u=f(t)$ 不检查结果、按预设一路执行；闭环 $u=f(e(t))$ 测量输出、与目标比较、按误差调整。精确判据（`11_term_disambiguation.md` §2.2）：**"反馈必须包含比较；不是所有循环都是反馈。"**

- **反例 → 正例**：

```js
// 反例（开环）：每次收到消息都无条件弹通知，不判断该不该弹
function onMessage(msg) {
  popup.show(msg)          // 来了就干，没有"比较"
}

// 正例（闭环）：先判断"重要吗 + 重复吗"，再决定弹不弹
let lastSeen = null
function onMessage(msg) {
  if (msg.important && msg.id !== lastSeen) {   // 比较
    popup.show(msg)
    lastSeen = msg.id                           // 记忆
  }
}
```

- **物理解释**：开环 = 对 TBPM 初态直接演化 10000 步不看中间结果；闭环 = SCF 迭代每一步都检查收敛。

- **自查**：我的动作，是由"当前状态 + 这次输入"**共同**决定的吗？还是只要输入来了就无条件动作？

### 原则 ② 显式建模状态（Explicit State Modeling）

- **一句话直觉**：把"程序现在处于什么状态"写清楚，别让它散落成一堆说不清关系的开关变量。

- **控制论概念**：状态空间模型 $\dot{\mathbf{x}}=A\mathbf{x}+B\mathbf{u}$——**系统 = 状态 + 状态如何被变换**。它引出两个基本问题：**可控性**（能否把系统驱动到目标态）与**可观性**（能否从输出推断内部状态）。

- **反例 → 正例**：

```js
// 反例：状态散落在三个 flag 里，没人说得清"现在到底啥状态"
// —— isConnecting=false 且 isConnected=false 且 hasError=false 意味着什么？只能靠猜
let isConnecting = false
let isConnected  = false
let hasError     = false

// 正例：一个状态字段 + 一张迁移表，所有合法状态和迁移一目了然
let state = 'idle'    // 取值只有：idle | connecting | connected | error
const transitions = {
  start: { idle: 'connecting' },
  ok:    { connecting: 'connected' },
  fail:  { connecting: 'error' },
}
function step(event) {
  const next = transitions[event]?.[state]
  if (next) state = next        // 非法迁移自动被忽略
}
```

- **物理解释**：状态 $\mathbf{x}$ ↔ 波函数，系统矩阵 $A$ ↔ 哈密顿量（差一个 $i\hbar$ 因子）。**可观测性 → 可测试性**：状态能被外部读取，系统才可诊断；状态散落 = 可观测性为零。

- **自查**：如果我问"程序现在处于什么状态"，能不能**一句话**答出来？还是得同时翻好几个变量才能拼出答案？

### 原则 ③ 负反馈稳定化（Negative Feedback for Stability）

- **一句话直觉**：高频、重复的事件要"降噪"——别每次刺激都响应，否则会刷屏、抖动、失控。

- **控制论概念**：负反馈削弱偏差 → 稳定；正反馈放大偏差 → 振荡或失控。控制增益 $K$ 太大就震荡发散。工程上有三个降增益手段：**去抖**（debounce）、**冷却**（cooldown）、**死区/迟滞**（deadband，等价施密特触发器）。

- **反例 → 正例**：

```js
// 反例：输入框每敲一个字符就发一次请求——敲 "hello" 发 5 次，浪费且抖动
input.on('change', () => search(input.value))

// 正例（去抖 debounce）：停止输入 300ms 后才发一次
let timer
input.on('change', () => {
  clearTimeout(timer)
  timer = setTimeout(() => search(input.value), 300)
})
```

死区的例子：恒温器若设在 25.0°C，且"低于 25 就开、高于 25 就关"，室温会在 24.99~25.01 之间**反复开关**（抖动）。给一个死区——"低于 24.5 开、高于 25.5 关"——就能稳定住。

- **物理解释**：SCF 的 mixing 参数 $\alpha$ 就是增益——$\alpha$ 太小收敛慢，太大震荡发散；去抖/冷却/死区就是"选一个不会发散的增益"。

- **自查**：同一个事件连续来 10 次，我的程序会动作 10 次吗？如果会，需不需要加阻尼？

### 原则 ④ 鲁棒性：优雅降级（Robustness: Graceful Degradation）

- **一句话直觉**：一个依赖（文件、网络、第三方）失败了，别让整个程序崩，要"退而求其次"。

- **控制论概念**：**BIBO 稳定**（有界输入 → 有界输出）与**鲁棒性 vs 最优性**的 trade-off（`11_term_disambiguation.md` §5）：鲁棒 = 对不确定性不敏感。旁路功能还应 **fail-open**（失败时不打断主流程）。

- **反例 → 正例**：

```js
// 反例：配置文件读不到就直接抛异常，整个程序崩溃
const config = JSON.parse(readFile('config.json'))   // 文件缺失 → throw，全崩

// 正例：主路径失败 → 回退默认值，程序照常运行
let config
try {
  config = JSON.parse(readFile('config.json'))
} catch {
  config = defaultConfig          // 优雅降级：退而求其次
}
```

更一般的形态是**回退链**：主通道 → 备用通道 → 兜底，每一级失败就落到下一级，直到"至少还有个能用"。

- **物理解释**：坏事件进来，坏影响不该传导出去——把"测量/外界耦合"的噪声挡在确定性核心之外。

- **自查**：如果某个外部依赖（文件/网络/第三方/权限）失败了，我的程序会崩溃吗？有没有退路？

## 3. 信息视角（communication）— 控制需要信息，通信需要契约

### 原则 ⑤ 明确信息契约（Explicit Information Contract）

- **一句话直觉**：只依赖"对方公开承诺的接口"，别偷看、别依赖对方的内部实现。

- **控制论概念**：Wiener 定义控制论为"动物和机器中的**通信与控制**"。控制的前提是有信息，信息要流动就必须有**双方约定的编码**——接口、类型、事件载荷、配置 schema，都是这种契约。

- **反例 → 正例**：

```js
// 反例：偷用库的"内部私有"字段，作者一改就静默崩坏
const result = library._internalCache.get(key)   // 下划线开头 = 内部实现，无契约保障

// 正例：只调用公开 API，行为有契约保障
const result = library.get(key)
```

契约不只是"函数名"，还包括：**参数的类型与顺序、返回值的结构、事件载荷里有哪些字段、出错时抛什么异常**。写代码时先问"我依赖的这条契约，对方承诺过会保持稳定吗？"

- **物理解释**：契约 = 传感器读数的"量纲约定"。量纲（契约）一旦悄悄改变，所有下游计算（消费方）静默出错。

- **自查**：我依赖的字段/函数，是对方**公开承诺**的，还是我偷看了它的内部？换个版本会不会就碎？

### 原则 ⑥ 副作用隔离（Side-Effect Isolation）

- **一句话直觉**：算数的函数别顺便做"别的事"（打印、写文件、发请求）；"纯计算"和"碰外部世界"要分开。

- **控制论概念**：反馈回路里有两类环节——**传感器/执行器**（接触不可预测世界的边界）与**控制器**（内部确定性的信息处理）。好设计把两者物理上分开。

- **反例 → 正例**：

```js
// 反例：算平均值还顺便打印、写日志——没法单独验证"算得对不对"
function average(nums) {
  const sum = nums.reduce((a, b) => a + b, 0)
  const avg = sum / nums.length
  console.log('计算完成', avg)   // 副作用混进来了
  return avg
}

// 正例：纯函数只算、只返回；打印交给调用方决定
function average(nums) {
  return nums.reduce((a, b) => a + b, 0) / nums.length
}
// 调用方想打印再打印
const avg = average(nums)
```

**纯函数**的定义只有两条：①同一个输入永远得到同一个输出；②不改变外部世界（不打印、不写文件、不修改变量）。满足这两条，它就能"离线"反复测试——这是测试成本的根源差异。

- **物理解释**：控制器 = 哈密顿量/演化算符（确定性的）；执行器 = 测量/与外界耦合（有噪声、会失败）。

- **自查**：我这个函数，除了"算出结果并返回"之外，还做了别的事吗（打印/写文件/发请求/改全局变量）？

## 4. 系统工程视角（design）— 把零件变成靠谱的整体

### 原则 ⑦ 功能分解 + 交互协议（Functional Decomposition + Interaction Protocols）

- **一句话直觉**：一个函数只做一件事；函数之间靠"参数 + 返回值"说话，而不是互相乱摸。

- **系统工程概念**："系统工程不能只做零件相加，它必须设计和理解**交互协议**"（`00_beginner_guide.md` §6.3）。软件版就是那句老话：**高内聚**（一个模块只干一件相关的事）、**低耦合**（模块间只通过窄接口通信）。

- **反例 → 正例**：

```js
// 反例：一个 200 行函数，读文件、解析、计算、格式化、写文件全挤在一起。
// 想改"输出格式"，被迫动到"计算"的代码——牵一发动全身
function processReport(path) {
  const text = fs.readFileSync(path)
  // ... 30 行解析 ...
  // ... 50 行计算 ...
  // ... 20 行格式化 ...
  // ... 10 行写文件 ...
}

// 正例：拆成各司其职的小函数，通过参数/返回值通信（接口 = 函数签名）
function processReport(path) {
  const data   = load(path)     // 只负责读 + 解析
  const result = compute(data)  // 只负责算
  save(format(result))          // 只负责写
  return result
}
```

`load`、`compute`、`save`、`format` 各自的**签名**（输入什么、返回什么）就是它们之间的"交互协议"——协议先于实现定下来，换掉任何一个都不会连累其它。

- **物理解释**：哈密顿量拆成动能项 + 势能项 + 相互作用项，各算各的，通过"基函数"这个接口耦合——换掉势能项不必重写动能项。

- **自查**：这个函数做了几件事？改其中一件事，会不会被迫动到另一件？

### 原则 ⑧ 涌现需要 V&V（Emergence Needs Verification & Validation）

- **一句话直觉**：每个零件都对 ≠ 拼起来能转。要分两层测：零件对不对（验证）、拼起来是不是你要的（确认）。

- **系统工程概念**：Anderson "more is different"——**单模块行为无法推导整体行为**。系统工程用 V&V 对付它，且要区分：**验证**（Verification，"做对了吗"）与**确认**（Validation，"做了对的东西吗"）。

- **反例 → 正例**（用流程而非代码说明）：

```text
反例：四个函数各自写了单测，全部通过 → 直接交付 → 第一次联调就崩
      原因：每个函数的"接口假设"各自为政，拼起来才发现对不上
      单测只能证明"零件本身没坏"，证明不了"零件之间配得上"

正例：分层测试
      验证 Verification  —— 每个函数单独测（单元测试）      → 零件做对了吗
      集成 Integration   —— 把函数拼起来测（集成测试）        → 拼对了吗
      确认 Validation    —— 整个程序真机跑（端到端测试）      → 做了用户要的东西吗
```

- **物理解释**：一个电子没有"拓扑"；$10^{23}$ 个电子在磁场+周期势中涌现出量子霍尔平台。同理，四模块各测通过 ≠ 插件真会弹窗——"弹窗"是涌现出来的整体行为。

- **自查**：每个零件都测过了，但**拼起来之后**真的测过吗？真机跑过吗？

### 原则 ⑨ 范围控制 + 明确非目标（Scope Control + Non-Goals）

- **一句话直觉**：别为"以后可能用"而写今天用不上的东西。

- **系统工程概念**：系统工程的定义是"确保设计**在做该做的事，而且没做不该做的事**"（`11_term_disambiguation.md` §1.2）。后者往往更难。警惕**复杂化**（complicated，零件多但可预测）伪装成**复杂**（complex，涌现）。

- **反例 → 正例**：

```js
// 反例：为"以后可能换数据库"写了 5 层抽象，现在其实只用一个数组存数据
class AbstractRepositoryFactory { /* ... */ }
interface IDataAccess            { /* ... */ }
class MongoDataAccess implements IDataAccess { /* ... */ }

// 正例：现在就一个数组，直接写清楚；真需要换库时再抽象也不迟
const items = []
function add(item)  { items.push(item) }
function all()      { return items }
```

这就是 **YAGNI**（You Aren't Gonna Need It）：不要实现你"目前"不需要的东西。每多一个抽象层，就多一个会坏的零件、多一份要维护的文档。

- **物理解释**：过度设计本身是一种不稳定——它增加了本不存在的失效面。鲁棒性 vs 最优性的权衡：**够用即最优**。

- **自查**：这段代码里有多少是"现在就用"的？多少是"以后可能用"的？后者能不能删掉？

## 5. 失效模式：违反原则的代价

通则的失效不是"某一种 bug"，而是**系统在某个环节丢掉了信息或能力**。它们在任意软件项目中都会出现。下表先给全貌，再逐条展开。

| 失效模式 | 一句话症状 | 违反的原则 |
|---|---|---|
| 可观测性丢失 | 从输出看不出内部状态，只能瞎猜 | ①② |
| 增益失控 | 事件风暴、抖动刷屏 | ③ |
| 契约漂移 | 接口悄悄改变，消费方静默出错 | ⑤ |
| 副作用泄漏 | 逻辑与外界纠缠，测不了也复不了用 | ⑥ |
| 开环结构 | 只反应不比较，对每个输入无条件动作 | ① |
| 范围蔓延 | 无退出条件的无限扩展、零件堆砌 | ⑨ |

**① 可观测性丢失**：状态散落在十几个全局变量里，出问题时你无法从"症状"反推"现在到底处于什么状态"。典型表现：加日志要看十几个变量；修复靠"改一改试试"。→ 治本：原则②把状态显式建模，让状态可读、可测。

**② 增益失控**：一个事件被正反馈反复放大——比如"A 触发 B，B 又触发 A"，或高频事件每次都全量响应，最终刷屏、卡死。典型表现：日志里同一动作刷了几百条；按钮被连点后重复提交。→ 治本：原则③去抖/冷却/死区，把增益降下来。

**③ 契约漂移**：你依赖的库升级了，内部字段改名，你的代码**不报错但结果全错**（静默失败，比崩溃更可怕）。典型表现：升级依赖后，测试全绿但功能悄悄变味。→ 治本：原则⑤只依赖公开契约 + 升级后回归测试。

**④ 副作用泄漏**：一个"算数"的函数里偷偷写了文件、发了请求，导致它无法单独测试、无法复用。典型表现：想复用一个函数，却发现它顺带做了三个不相干的事。→ 治本：原则⑥纯函数核心 + 副作用收口到外层。

**⑤ 开环结构**：对每个输入都无条件执行同一个动作，没有比较、没有记忆。典型表现：同一个事件触发了本该只执行一次的动作十次。→ 治本：原则①引入比较 + 记忆。

**⑥ 范围蔓延**：为"以后可能用"持续加零件，没有退出条件，最后系统零件数远超实际需要，每个都是潜在故障点。典型表现：一个简单功能套了五层抽象。→ 治本：原则⑨显式非目标 + YAGNI。

> 这张表是"通则级"的。下一部分会看到 `dsh-notify` 把每一类失效具体化成了 F1–F6。

# 第二部分（次）：dsh-notify 如何体现这些原则

## 6. 层次一 · 产品内（控制论）：插件本身的设计

### 6.1 观察器建模：产品 = 一个旁路反馈控制器

`dsh-notify` 订阅宿主的 agent 状态事件，在"整轮任务完成"时经 WSL→Windows 弹 toast。把它的产品结构对到总纲的五要素：

| 控制论元件 | dsh-notify 落点 |
|---|---|
| 设定值 (reference) | `Config`（schemastery：`notifyOnComplete` 等） |
| 传感器 (sensor) | `ctx.on('agent/status', handler)` |
| 控制器 (controller) | `tracker.js`（纯函数状态机 + 冷却） |
| 执行器 (actuator) | `sender.js`（spawn 弹窗） |
| 被控对象 (plant) | DSH 宿主 + Windows 通知系统 |

它被刻意设计成**观察器**而非**参与者**：只读宿主信号、只对外界动作，不修改宿主任何状态（原则②⑥）。

### 6.2 模块划分：功能分解 + 窄接口

| 模块 | 单一职责（内聚） | 对外窄接口（耦合） |
|---|---|---|
| `toast-script.js` | 文本 → PowerShell 脚本 | `buildPowerShellScript({title,body,sound})` |
| `tracker.js` | 状态迁移 + 冷却决策 | `createTracker({cooldownMs}).update(...)` |
| `sender.js` | 真正发送（副作用） | `sendNotification(title,body,opts,logger)` |
| `index.js` | 组装与接线 | `apply(ctx, config)` |

### 6.3 原则 → 代码落点（映射表）

| 通则 | 产品内落点 |
|---|---|
| ① 闭环优于开环 | `ctx.on('agent/status')` + tracker 状态机（比较迁移，而非盲发） |
| ② 显式状态 | tracker 的 per-agent `{ lastStatus, lastNotifiedAt }`，`reset()` 保证可观 |
| ③ 负反馈稳定化 | `cooldownSec` 冷却 + 死区（`prev===next` 不触发）+ `rootOnly` 过滤 |
| ④ 鲁棒·优雅降级 | sender 三级链 powershell → notify-send → console；`sendToast` 永不 reject |
| ⑤ 信息契约 | `Config` schema + `agent/status` 公开载荷 + `session.header.parentSession` |
| ⑥ 副作用隔离 | toast-script / tracker 纯函数，仅 sender 碰 spawn |
| ⑦ 功能分解+协议 | 四模块 + 导出函数签名即交互协议 |
| ⑧ 涌现需 V&V | 产品侧：纯函数可离线单测（可观测性）；过程侧见 §7 |
| ⑨ 范围控制+非目标 | 无持久化、无悬浮窗、无历史记录（最小侵入） |

### 6.4 三层边界与失效模式

产品设计被三条边界约束，跨边界只走既有合法接口（原则④⑤）：

- **插件 ↔ 宿主（契约边界）**：只读 `agent/status` 事件与 `session.header`，不碰宿主内部。
- **WSL ↔ Windows（OS 边界）**：唯一合法通道是 `powershell.exe` interop。Electron 悬浮窗在 WSL 下失败，正是"执行器不在目标平台"。
- **宿主状态 ↔ 用户注意力（信息边界）**：把高频状态流翻译成低频感知，靠 §6.3 的调理动作。

`dsh-notify` 的七类失效是 §5 通则失效的实例化（F7 为真机验证后复盘补入，见 §15.1）：

| 失效 | 症状 | 违反的通则 | 防御 |
|:---:|---|---|---|
| F1 执行器不在目标平台 | 悬浮窗静默失效 | ④ | 选 powershell interop，不选 Electron |
| F2 传感器寻址错误 | 订阅不到事件/注入错服务 | ⑤② | 钩子核实（§7） |
| F3 供应链漂移·年龄门禁 | 老依赖缺新 API | ⑤ | 零第三方运行时依赖 + 维护期检测 |
| F4 执行器权限扰动 | powershell 被 ExecutionPolicy 拦截 | ④ | 三级降级链 |
| F5 子 agent 风暴 | 子 agent 各自触发刷屏 | ③ | `rootOnly` + 冷却 |
| F6 动作终端不可观测 | toast 是否显示无法感知 | ① | 尽力而为 + 文档排障 |
| F7 执行器假成功 | 执行器静默失败却报告成功，回退链失效 | ①④ | 用可验证的成功判据，而非进程退出码 |

## 12. 出现的问题

### 12.1 执行器「假成功」——贯穿全程的根问题

这是唯一的根问题，在**三个层面**反复发作：

1. **`sender.js` 的 `notifySend` 假成功**（编写期已知、已修）：`spawn` 对"命令不存在"并不同步抛错，而是异步 `error`；原代码却同步 `return true`，console 兜底永远走不到。
2. **toast 脚本的假成功**（真机暴露的根因）：`CreateToastNotifier('DeepSeek Harness')` 用了**未注册的 AUMID**，WinRT `Show()` 静默失败，但 PowerShell **仍以 exit 0 退出**。于是 `sendToast` 判断"exit 0 = 成功"，回退链在第一级就"成功"终止——既没 toast 也没 console 日志，表现为"完全无反应"。

两例同构：**执行器层静默失败 + 观察器只看表面信号（同步返回值 / 进程退出码）**。

### 12.2 诊断误判（global 弯路）

把"完全无反应"误判为"缺 `{ global: true }`"。事后从 `dsh-scope` 的 `scopeTarget` 源码看，它的 filter 对**无 scope tag 的全局监听器**（`scopeOf(ctx) === undefined`）本就返回 `true`——即全局 ctx 上不带 global 的监听器也能收到事件；`global: true` 只在"监听器 ctx 自身被 scope 标记"时必需（`dsh-agent/invariant.js` 的 install ctx 即属此列）。那次 global 修复是**不必要但无害**的，不是根因。

### 12.3 重启混乱（EADDRINUSE）

旧 `dsh web` 占着 3080，新进程起不来；且旧进程正是承载 Web GUI 会话的进程，加剧了"要不要 kill"的纠结。属操作层问题。

## 13. 根因（为什么）

### 13.1 观察器拿到的"成功信号"与真实成败脱钩（违反原则①）

闭环要求"感知 → 比较 → 调整"，但 `sendToast`/`notifySend` 的"比较"只比对了 `exit code` / 同步返回值，而这两个信号在 PowerShell 非终止错误、`spawn` 异步 `error` 下**不反映真实成败**。原则①的反例是"来了就干"，这里更深一层：**"干了"之后没有"真的成了"的验证**。

### 13.2 契约的静默违约（违反原则⑤）

WinRT 的 AppId 是一条契约——必须用已注册 AUMID。`'DeepSeek Harness'` 违约了，但 WinRT 的"惩罚"是**静默失败**：不抛异常、exit 0。这正对应 §5 失效模式③"契约漂移"里最阴险的一种——"不报错但结果全错"。

### 13.3 可观测性缺失 → 诊断靠猜

- `sendToast` 用 `stdio: 'ignore'`，PowerShell 内部错误被丢弃；
- 插件无任何日志，真机上无法区分"handler 没收到事件" vs "收到事件但 toast 静默失败"；
- 于是诊断在**没有反馈**时用"读源码 + 推测"替代了"建立反馈 + 观察"，才误判 global。

一旦加了 `[diag]` 日志，三行输出（`apply called` → `event status=...` → `delivered via channel=powershell`）**一锤定音**锁定了 AppId——印证本文结尾的核心句"可观测性决定诊断力"。

### 13.4 V&V 层级错位（违反原则⑧）

单测（验证 `toast-script.js` 生成的脚本文本正确）+ `--dump-config`（验证配置挂载）全绿，但都验证不到"toast 真的弹出来"——那是**涌现行为**，只有真机 Validation 能验证。编写期"已达标"的判断是**验证层**的，覆盖不到**确认层**。

## 14. 解决

| 问题 | 解法 |
|---|---|
| `notifySend` 假成功 | 改 `Promise<boolean>`，等 `exit`/`error` 再 resolve，删无用 `--version` probe |
| AppId 未注册 | 默认 AppId 改为 `powershell.exe` 的 AUMID `{1AC14E77-02E7-4E5D-B744-2EB1AE5198B7}\WindowsPowerShell\v1.0\powershell.exe`（`toastit.dev` 证实"hard code 到 powershell.exe 的 AppId 才能显示"） |
| 诊断误判 | 加 `[diag]` 日志建立可观测性，用真实信号取代推测 |
| 重启混乱 | kill 旧进程 → 前台 `dsh web` 重新加载新代码 |

## 15. 教训与通则修订

### 15.1 新增失效模式 F7「执行器假成功」

F6"动作终端不可观测"原只被当作"用户侧不可感知、尽力而为"。但这次证明它不只是"看不见结果"，而是会**反过来污染回退链**——因为不可观测，`sendToast` 把 exit 0 当成功，回退链在错误层级终止。故补入 F7（见 §6.4 表）：**执行器静默失败却报告成功**，违反原则①④，防御手段是"用可验证的成功判据，而非进程退出码"。

### 15.2 原则④自查的补充

优雅降级有一个隐藏前提：**每一级必须如实报告成败**。假成功会让整个回退链失效。原则④的自查应加一条："我的降级判断，依据的是真实结果，还是进程退出码 / 同步返回值这类可能骗人的信号？"

### 15.3 "已达标"只是 Verification，不是 Validation

草稿模块（尤其 `toast-script.js`）的"达标"是纯函数 / 结构正确，真机弹窗这一层没被覆盖。原则⑧的分层测试（验证 / 集成 / 确认）恰恰为此设计——本次最终也确实是靠"真机 Validation + 可观测日志"才定位的。

### 15.4 契约要按上下文理解（global 的 nuance）

同一条 `ctx.on('agent/status', ...)`，在**无 scope tag 的全局 ctx** 上无需 `global: true`，在**被 scope 标记的 ctx**（如 `invariants.register` 传入的 install ctx）上才必需。`dsh-agent/invariant.js` 用 `global: true` 不代表全局 ctx 也必须用——契约的语义随监听器的 scope 归属而变。这提醒：核实源码时，既要看"对方怎么写的"，也要看"对方在那个上下文里为什么需要那样写"。

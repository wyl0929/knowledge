# 23 最小可行实验计划

Last updated: 2026-08-30

## Gate requirements / 门控要求

Core Claims Gate 与 Operationalization Gate 已执行（17 号文件）。P1 的 operational_status 为 `provisional`，因此本 MVP 是**消歧型 MVP**：它首先验证测量定义（框架编码手册）、任务可行性（双平台事件取样）与读出流程（编码管线），**不验证也不声称任何机制结论**。

## 用人话说这个 MVP

这个 MVP 只回答一个问题：**"你的研究设计到底能不能落地？"** 用佩洛西访台（2022.08）一个事件做全链路试点——

- 结果 A（取样+编码都通）：P1 按原设计推进，试点图直接进论文第一章；
- 结果 B（Yahoo 通、X 不通）：P1 的 X 侧改成"2021–2023 学术 API 窗口数据集 + 2026 前瞻采集"，研究问题不变、时段边界改写；
- 结果 C（编码信度不达标）：框架清单简化（只编四功能中的 2–3 功能），或转全人工小样本；
- 结果 D（全都不通）：止损，改题方向（见 22 号 P1 止损标准与下方"失败后的下一步"）。

## Operationalization Contract / 任务可操作化契约

### 声称要验证的任务

消歧任务：在 1 个涉台事件上验证 (a) Yahoo News 与 X 两平台的事件窗口文本可获取并可比；(b) 框架编码手册 v0.1 跨平台可复现（人-人 α、人-机 α 达标）；(c) 框架分布试点图可读、可解释。

### 输入对象与允许输入集合

佩洛西访台事件（2022.08.02 前后 14 天窗口）× 两平台：

- Yahoo 侧：Wayback CDX 快照抓取（news.yahoo.com 涉台关键词页面）+ Media Cloud 检索（若收录）+ 订阅库（若可用）三者取并集；
- X 侧：CMU Kilthub 佩洛西数据集（元数据与许可待核验）或第三方历史 API 试采（成本待评估）或公开数据集拼合；
- 编码子样本：两平台各 ≥50 条，总计 ≥100 条（跨平台分层）。

### 编码、控制、演化、解码与读出流程

```text
输入：事件窗口两平台文本（可得部分）
  -> 清洗（去重；来源标签；机器账号标记——可用则做，不可用则记录）
  -> 编码制备（新闻取标题+导语；推文取全文）
  -> 框架编码（手册 v0.1：Entman 四功能元素 + 涉台候选框架清单）
      人工双编码员 ≥50 条子样本；LLM 同手册全量编码
  -> 读出（α 人-人、α 人-机、不可编码率、框架分布）
  -> 指标计算与判定（对照下方成功/止损标准）
  -> 结论（消歧结论 + P1 升级/降级决策）
```

### 目标变换

文本 → 四功能元素标签 → 框架标签（元素组合规则）→ 事件-平台框架分布 P(f)。

### 指标定义

- 指标：人-人 Krippendorff's alpha（框架标签层）。
- 计算方式：按 16 号文件公式，双编码员子样本。
- 真正测到了什么：手册 v0.1 的跨编码员稳定性。
- 没有测到什么：手册是否"对"（效度，需专家复核）。
- 依赖假设：编码员经过同标准训练（依赖 C1、G4）。

- 指标：人-机 alpha 与 F1（LLM vs 人工黄金标准）。
- 计算方式：同一子样本、同一手册、锁定提示版本。
- 真正测到了什么：LLM 可否代理人工做全量编码。
- 没有测到什么：模型泛化到其他事件的表现（需第二事件留出验证）。
- 依赖假设：人工标准本身可靠（以人-人 α 为天花板）。

- 指标：平台样本可得性矩阵（可得文本量、时间覆盖、来源标签完整度）。
- 计算方式：三路探测的计数与覆盖表。
- 真正测到了什么：取样路径的现实容量。
- 没有测到什么：样本的代表性（只能定性报告偏差方向）。
- 依赖假设：探测窗口（14 天）对事件覆盖充分。

### 失败事件、泄漏、损失与后选择政策

- 取样失败事件计入可行性矩阵并显式报告（不静默替换路径）；某平台 0 获取 → 触发结果 B/D 决策。
- 编码失败（不可编码文本）计入总样本分母，报告不可编码率；不事后删除"不方便"的文本。
- LLM 提示版本锁定（记录模型+版本+prompt hash）；不按试点结果改提示再重跑（防止后选择美化）。
- 机器账号清洗：可做则报告清洗比例与前后分布；不可做则显式声明未清洗（conditional 与 unconditional 都要出现在报告里）。
- 信度只报告一次主分析 + 敏感性分析（如剔除稀有框架后），不挑选子集凑 α。

### Baseline 公平性

- 人工编码与 LLM 编码：同子样本、同手册、同预算口径（人工小时 vs API 美元分开报告）。
- 两平台比较：同事件窗口、同聚合粒度（天）；任何平台特有的预处理（如推文去重）在两平台可比单元上说明。
- 流向/演变不进入本 MVP（那是 P1 主分析）；本 MVP 不给任何机制结论。

### 阳性结果能证明什么

取样路径可行、编码手册 v0.1 可复现、两平台框架分布可比、试点图可读——P1 可升级为完整执行版。

### 阳性结果不能证明什么

不能证明框架演变、跨平台流向、机制归因；不能外推全时段代表性与全美民意。

### 阴性结果意味着什么

按平台/编码两个维度分别触发 22 号 P1 的重定义预案（结果 B/C/D）。

### operational_status

**operational_status: provisional**（本 MVP 即消歧任务；完成后按结果升级为 metric_checked/resource_checked 或改题）。

## 最小模型 / 核心方程 / 实验流程

本 MVP 的核心对象是框架分布：

$$
P_{platform}(f) = \frac{n_{platform,f}}{\sum_{f'} n_{platform,f'}}, \quad f \in \mathcal{F}_{v0.1}
$$

其中 n 为试点窗口内已编码文本数，F_{v0.1} 为手册 v0.1 的框架集合；比较对象是两平台的 P(f) 差异（试点图）与编码信度 α。

实验流程：

```text
事件窗口文本（Yahoo 三路 + X 可得子集）
  -> 清洗与编码制备
  -> 手册 v0.1 编码（人工子样本 + LLM 全量）
  -> 信度与不可编码率计算
  -> P(f) 试点图与可行性矩阵
  -> 对照成功/止损标准 → 升级/降级/改题决策
```

## 实验计划

### MVP 标题：佩洛西访台事件双平台取样与框架编码全链路试点（P1 消歧）

### 研究问题：用户研究设计（P1）在数据层与测量层是否可落地？

### 最小可行假设：

H1（取样）：事件窗口内 Yahoo News 与 X 各可获得 ≥100 条涉台相关文本（任一可得路径）。
H2（测量）：框架编码手册 v0.1 在双平台子样本上达到人-人 α ≥ .67（探索级）。
H3（代理）：LLM 编码与人工黄金标准的人-机 α ≥ .67 或 F1 ≥ .75（阈值惯例，具体出处 NEEDS_VERIFICATION）。

### 输入：佩洛西事件窗口（2022.08.02±14 天）两平台文本 + 手册 v0.1 + LLM API。

### 需要实现的代码：

1. `fetch_yahoo_wayback.py`：CDX API 查询 news.yahoo.com 涉台页面快照并下载清洗（关键词：Taiwan, Tsai, Pelosi, Taipei, strait）。
2. `probe_mediacloud.py`：Media Cloud API 检索 Yahoo News 收录与事件窗口覆盖。
3. `prep_x_sample.py`：X 子集加载（Kilthub CSV / 第三方 API 输出）、去重、时间窗过滤。
4. `codebook_v0.1.json`：四功能元素 + 涉台候选框架清单（结构见 14 号文件 C1/MattKohr08）。
5. `llm_code.py`：锁定提示版本的批量编码 + 输出 JSONL（含理由字段）。
6. `reliability.py`：Krippendorff's alpha（可用 krippendorff 包）、F1、不可编码率报表。
7. `pilot_plot.py`：双平台框架占比并排图 + 可行性矩阵表。

### 需要的数据：X 佩洛西数据集（Kilthub，许可待核验）或第三方 API 试采；Wayback 快照；Media Cloud 账户（免费层）。

### 对比基线：Media Frames Corpus 通用框架对试点文本的覆盖比例（评估"涉台专属框架是否需要"）；未清洗 vs 清洗后的分布对比（若可清洗）。

### 评价指标：可得文本量、时间覆盖、人-人 α、人-机 α/F1、不可编码率、通用框架覆盖比例。

### 预期关键图：图 1 双平台框架占比并排条形图；图 2 编码信度表（人-人/人-机/不可编码率）；图 3 数据可行性矩阵热图。

### 第一周计划：

1. 完成 `fetch_yahoo_wayback.py` + `probe_mediacloud.py`，产出 Yahoo 侧可行性矩阵（CDX 快照数、可解析正文数、来源标签比例）。
2. 核验 CMU Kilthub 佩洛西数据集元数据与许可；不可行则向第三方历史 API 询价试采（Sorsa 类），产出 X 侧可行性结论。
3. 起草 `codebook_v0.1.json`（以 Entman 四功能 + 战略模糊/中国威胁/民主同盟/危机管理/经济利益等候选框架），并准备 50 条人工编码训练材料。

### 第一个月计划：

1. 第 1 周：上述取样探测 + 手册 v0.1 定稿（与领域专家复核一次）。
2. 第 2 周：人工双编码员试编 20 条校准 → 正式编码 ≥50 条子样本；跑 `reliability.py` 得人-人 α。
3. 第 3 周：`llm_code.py` 全量试点编码 + 人-机 α/F1；不可编码率报表。
4. 第 4 周：`pilot_plot.py` 出三张图；写消歧结论（结果 A/B/C/D 判定）；更新本文件实验记录与 17 号文件 operational_status。

### 成功标准：

H1+H2 同时成立（两平台各 ≥100 条、人-人 α ≥ .67）即 MVP 成功；H3 成立则 LLM 管线获准进入全量编码，不成立则回退全人工。所有失败事件（取样失败、不可编码文本）已在可行性矩阵与报表中显式出现，无静默后选择。

### 止损标准：

- 第 1 周末 X 侧全部路径失败 → 执行结果 B 预案（时段重定义），MVP 目标改写后继续；
- 第 4 周末人-人 α < .60（两轮手册迭代后）→ 执行结果 C 预案（简化框架清单/纯人工）；
- 两平台均无法获得 ≥30 条文本 → 执行结果 D，停止 P1 原设计，改题讨论（记录到 90_QA.md）。

### 成功后的下一步：P1 升级（operational_status → metric_checked 复核），扩展到 9–12 个事件 × 三阶段，执行 G1/G2/G3 全量分析。

### 失败后的下一步：按 B/C/D 预案改题或降级，更新 22 号 P1 与 20 号 gap 表，记录 99_update_log。

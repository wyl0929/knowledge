# 案例研究: 研究工作流中的偏差响应 — 层级归因与跨层级排除

> **领域标签**: 系统科学 · 控制论 · 诊断方法论 · 研究工作流 · 决策理论
> **时间跨度**: 2026-06-21 ~ 2026-07-19 (约 4 周，持续迭代)
> **相关项目**: `/home/wyl/project/MG/` (multilayer graphene QHE)
> **关联案例**:
>   - `91_case_study_hall_conductance_baseline.md` — Hall 电导基线偏移 (Level 1 症状 → Level 1 根因，但被误诊为 Level 3)
>   - `92_case_study_sigmaxx_parameter_optimization.md` — σ_xx 五维参数扫描 (Level 2 响应，实验设计缺陷)
> **核心协议**: `/home/wyl/.agents/skills/debug-workflow/SKILL.md` (v1.0 → v2.0 修订)
> **相关文档**: `MG/docs/blue_print.md`, `MG/docs/Phase3X_sigmaxx/plan.md`, `MG/docs/Phase_pre/plan.md`

## 摘要

在多层石墨烯量子霍尔效应的计算研究中，项目遵循「blueprint (战略) → plan (战术) → tasks (操作)」的三层递阶架构。当计算结果偏离预期（出现 NaN、基线偏移、噪声过大）时，研究者面临一个核心困境：**症状的表观大小与根因的深度无关**。一个导致所有输出为 NaN 的故障可能只是一行 YAML 参数错误（修复成本 1 分钟），也可能需要重写 C++ 核心算法（修复成本数周）。

此前 4 周中，项目经历了两次大规模的诊断事件——Hall 电导基线偏移（案例 #1）和 σ_xx 收敛失败（案例 #2、Phase 3X）。回顾这两次事件中的决策过程，暴露出一个系统性的应对模式缺陷：**偏差出现后，响应层级的选择依赖于研究者的直觉和局部经验，而非结构化的判别协议**。具体表现为：

- **层级误判**：基线偏移被当作算法缺陷（Level 3）诊断了 10 天，最终发现是参数错误（Level 1）
- **过度反应**：σ_xy 问题未定位时即引入了替代引擎 quantum-kite（Level 3 战略转向），后证实不必要
- **反应式膨胀**：Phase 3X 从计划的 5 个子步骤膨胀到 A–E-3 共 8 个子 Phase，无退出条件
- **文档反馈断裂**：Phase 3X 确认的已知限制（Γ·μ 噪声不可消除）未能显式传递到 Phase 4 plan

本文以控制论和系统工程的视角，将研究工作流建模为三层递阶反馈控制系统，分析旧应对模式中的信息流缺陷，并提出基于**跨层级排除**和**偏差升级协议**的新应对框架。核心改进包括：(1) 五类偏差分级标准 (I–V)；(2) 跨层级判别测试设计——每一步同时排除多个层级；(3) 诊断 Phase 与研究 Phase 的显式区分与生命周期管理；(4) 从诊断结论到 blueprint/plan 的自动反馈路径。

## 1. 系统建模：研究工作流作为三层递阶控制系统

### 1.1 三层架构

将 MG 项目的研究工作流抽象为控制系统，存在三个清晰的层级：

```
                        ┌─────────────────────────┐
                        │  Level 3: 战略层         │
                        │  blue_print.md           │
                        │  ─────────────           │
                        │  设定点: 研究目标        │
                        │  控制器: Phase 划分      │
                        │  执行器: create-plan     │
                        │  周期: 周–月             │
                        └──────────┬──────────────┘
                                   │ 偏差信号 (阻塞/证伪)
                        ┌──────────▼──────────────┐
                        │  Level 2: 战术层         │
                        │  Phase N/plan.md         │
                        │  ─────────────           │
                        │  设定点: Phase 交付物    │
                        │  控制器: 实验矩阵设计    │
                        │  执行器: gen_cfg.py      │
                        │  周期: 天–周             │
                        └──────────┬──────────────┘
                                   │ 偏差信号 (NaN/不收敛)
                        ┌──────────▼──────────────┐
                        │  Level 1: 操作层         │
                        │  tasks.md + SLURM        │
                        │  ─────────────           │
                        │  设定点: 单次计算结果    │
                        │  控制器: YAML 参数       │
                        │  执行器: sbatch          │
                        │  周期: 分钟–小时          │
                        └─────────────────────────┘
```

**反馈信号**（观测输出与预期的偏差）在 Level 1 产生，沿层级向上传递。每一层有自己的控制器（研究者 + AI）、执行器（工具链）和传感器（输出数据分析）。

### 1.2 核心困境：可观测性不足

在控制论中，**可观测性**指的是从输出信号能否唯一推断系统内部状态。本工作流的可观测性极差：

| 症状 | 可能的根因层级 | 修复成本跨度 |
|------|:---:|:---:|
| 输出全为 NaN | Level 1 (rescale 设小了) → Level 3 (Chebyshev 递推发散) | 1 分钟 ~ 数周 |
| σ_xy 基线偏移 | Level 1 (`num_integ_steps` 不足) → Level 3 (随机游走+浮点精度) | 改一行 YAML ~ 重写 C++ 核心 |
| σ_xx 无 LL 峰 | Level 1 (γ=0 未加无序) → Level 5 (KPM 对此体系根本不可用) | 加参数 ~ 换工具链 |
| DOS/LDOS 无 LL 结构 | Level 1 (B 场参数错误) → Level 3 (Peierls 相位实现 bug) | 改参数 ~ 修代码 |

**症状的表观严重性与根因深度之间没有相关性。** 这一事实是旧应对模式失效的根本原因。

## 2. 旧应对模式分析

### 2.1 模式描述

在 2026-06-21 至 2026-07-17 期间，项目在遇到偏差时遵循一种**隐式的、直觉驱动的层级分配**模式：

```
观测到偏差
    │
    ▼
"这个问题看起来大/小" ←── 直觉判断
    │
    ├── "小问题" → 在 Level 1/2 处理 (改参数、加扫参)
    │         │
    │         ├── 如果碰巧修好了 → ✅ (如 rescale=9→-1)
    │         └── 如果没修好 → 升级到 Level 3
    │
    └── "大问题" → 在 Level 3 处理 (新建 Phase、换工具链)
              │
              ├── 如果确实是 Level 3 → ✅ (如 Phase PRE)
              └── 如果本质是 Level 1 → ❌ 过度反应 (如 quantum-kite)
```

### 2.2 失败案例 1: Hall 基线偏移的层级误判 (案例 #1)

**事件序列**:

| 阶段 | 采取的层级 | 行动 | 实际层级 | 后果 |
|------|:---:|------|:---:|------|
| 2026-06-21: 首次发现 M>2560 时 σ_xy 偏移 | — | 怀疑 Chebyshev 递推发散 | — | 方向正确，但未检查 θ 积分参数 |
| 2026-06-22~27: VBL Phase A–M | **Level 3** | 9 假说系统排查，最终收敛到"条件收敛+随机游走" | **实际是 Level 1** (Nyquist 混叠) | 诊断本身方法论正确，但追逐的是混叠产生的伪影而非独立现象。消耗 6 天。 |
| 2026-06-27~30: 战略转向 | **Level 3** | 引入 quantum-kite 替代引擎做交叉验证 | **实际是 Level 1** | 过度反应。在根因未确定时切换工具链。 |
| 2026-07-01: Phase 0 save/load | Level 2 | 意外发现 `num_integ_steps < num_kernel` 时偏差 | — | 幸运的偶然发现。改变一行 YAML → 问题消失。 |

**根因分析**: VBL 诊断没有错——它正确排除了 9 个假说，确认了噪声注入和 Γ 权重的数学关系。但它犯了一个**层级定位错误**：将 Level 1 的问题（参数错误）当作 Level 3 的问题（算法缺陷）来诊断。这是**可观测性不足**的直接后果——Nyquist 混叠产生的 σ_xy 偏移与浮点随机游走产生的偏移在症状上不可区分。

**关键教训**: 在假说生成阶段 (Phase 2)，**没有将"默认参数值错误"作为一个独立的假设纳入矩阵**。如果 H0 是 "`num_integ_steps=2048` 对于 M>2048 不足"，一个实验即可确认。

### 2.3 失败案例 2: σ_xx Phase 3X 的反应式膨胀 (案例 #2)

**事件序列**:

| 阶段 | 原计划 | 实际 | 膨胀原因 |
|------|------|------|------|
| Phase A | 扫描 {γ, m, M, rs} | 按计划，但 γ 仅取 3 水平 | 事后发现最优值在边界上 |
| Phase B | int 扫描 3-9 个 | 扩展为 18 个 (增加了 m, M 维度) | 发现 M-int 耦合需要解耦 |
| Phase C | 汇总分析 | 按计划 | — |
| Phase D | — (原计划无) | **新增**: 种子平均验证 (SR=20) | 怀疑散粒噪声 → **被证伪** |
| Phase E | — (原计划无) | **新增**: rescale 移位判别 | 发现 0.6 eV 收敛异常 |
| Phase E-2 | — (原计划无) | **新增**: PSD 特征值截断 | Gram PSD 假说 → **被证伪** |
| Phase E-3 | — (原计划无) | **新增**: quad precision 递推 | 浮点精度假说 → **被证伪** |

**从 5 个子步骤膨胀到 8 个，其中 3 个是证伪实验。** 这不是失败——证伪实验具有高信息价值。但问题在于：

1. **无退出条件**: Phase 3X 何时算"完成"？最初是"确定五维最优参数"，后来变成"找到所有不可消除的噪声源"。这个目标的漂移没有在 blueprint 中显式记录。
2. **下游阻塞未动态管理**: Phase 3X "阻塞 Phase 4"，但当 D/E-2/E-3 连续证伪后，实际上已经说明 σ_xx 的 Γ·μ 噪声在当前框架内不可消除。此时应该触发的是 **降级 Phase 4 中的 σ_xx 目标**，而非继续寻找修复方案。
3. **诊断 Phase 与研究 Phase 无区分**: Phase 3X 在 blueprint 中被标记为研究 Phase，但它本质上是诊断 Phase。两者的退出条件和成功判据不同。

### 2.4 旧模式的系统性缺陷总结

| 缺陷 | 症状 | 控制论对应 |
|------|------|------|
| **层级误判** | Level 1 问题被当作 Level 3 诊断 | 观测器设计错误——从输出信号无法反推状态 |
| **过度反应** | 未确认根因即切换工具链 | 控制器增益过高——对小偏差信号施加了大幅控制动作 |
| **反应式膨胀** | 无退出条件的无限假设检验 | 无积分器重置——控制器状态持续累积但无收敛判据 |
| **文档反馈断裂** | 诊断结论未传递到下游 plan | 前馈路径缺失——已知限制未预补偿到后续 Phase |
| **无历史先验利用** | 每次遇到 NaN 都从零开始诊断 | 无自适应控制——系统模型不随经验积累而更新 |

## 3. 新应对框架：跨层级排除与偏差升级协议

### 3.1 设计原则

新框架基于三个核心洞察：

1. **不做层级猜测，做跨层级判别**：在信息为零时，设计每个诊断步骤能同时排除多个层级，而非先猜测层级再针对性诊断。
2. **偏差分层级响应，而非按症状响应**：根因属于 I–V 类中的哪一类决定了修复的规模和文档化路径，而非症状的严重性。
3. **诊断 Phase 是一等公民**：在 blueprint 中显式区分 [研究] Phase 和 [诊断] Phase，后者有独立的进入条件、退出条件和时间盒。

### 3.2 偏差升级协议 (Deviation Escalation Protocol)

| 偏差类型 | 判定标准 | 应处理层级 | 典型响应 | MG 案例 |
|:---:|------|:---:|------|------|
| **I 类：参数/配置错误** | 单一参数修改即修复，物理管线无缺陷 | Level 1/2 | 修正 YAML → 重跑 → 更新模板 | `rescale=9`→`-1`；`num_integ_steps < M` |
| **II 类：收敛条件不满足** | 需多维参数扫描确定安全窗口 | Level 2 (plan 内新子 Phase) | 矩阵扫描 → 确定最优参数 → 回写约束 | Phase 3X A–C: γ/m/M/rs/int |
| **III 类：算法/物理假设证伪** | 原假设被实验排除 | Level 2→3 (plan 内新 Phase + blueprint 阻塞标记) | 假设检验 → 证伪 → 接受限制 或 降级 | Phase 3X D/E: SR/rescale/PSD/quad 证伪 → Γ·μ 不可消除 |
| **IV 类：基础设施缺陷** | 同一类问题反复出现 | **Level 3 (新 [诊断] Phase)** | 系统性重构 → 参数校验自动化 | Phase PRE: 参数管理重构 |
| **V 类：物理预期错误** | 预期基于错误推导或文献误读 | **Level 3 (战略转向)** | 重审文献 → 修正目标 → 修订 blueprint | （预案）Kubo-Bastin σ_xx 对该体系不可用 |

### 3.3 跨层级判别序列

核心操作：**不猜测层级，而是设计诊断步骤，每一步同时排除多个层级。**

以 NaN 类故障（最常见的 MG 故障）为例的判别模板：

```
D1 [0 成本，利用已有数据]:
  检查低参数极限（小 B/小 M/小 m）是否正常
  → 正常: 排除 III (代码 bug) + V (物理不可能)
  → 也坏: 排除 I (不是参数能修好的)，升级到 III/IV

D2 [1 个作业，检验最可能的 Level 1 根因]:
  改变历史上最高频的可疑参数（如 rescale 加倍）
  → 修复: 确认 I 类
  → 未修复: 排除该参数

D3 [1-2 个作业，与 D2 并行，检验正交维度]:
  改变与 D2 参数正交的参数（如 B 减半）
  → 综合 D2+D3 的结果可区分 I vs III

D4 [如果 D2/D3 均未修复]:
  构造 MWE（极限缩小超胞/时间步/能量窗）
  → 正常: II 类（收敛条件不满足）
  → 仍坏: III/IV 类（算法或基础设施缺陷）
```

**关键特征**: 每步的结论都缩小可能层级空间，而非仅判断一个参数是否敏感。D1 零成本；D2 和 D3 可并行。

### 3.4 诊断 Phase 的生命周期

在 blueprint 中，诊断 Phase 与研究 Phase 有本质区别：

| 特征 | 研究 Phase (如 Phase 4) | 诊断 Phase (如 Phase 3X) |
|------|------|------|
| **目标** | 产出物理结果 | 确定计算方法的可行性边界 |
| **进入条件** | 前序 Phase 完成 | 观测到异常偏差，阻塞 ≥1 个下游 Phase |
| **退出条件** | 交付物达标 | 根因确认 + 已知限制明确 + 参数安全窗口确立 |
| **时间盒** | 按计划工期 | 建议 ≤ 2 周；超时触发战略重评估 |
| **产出** | 物理数据 + 图表 | 已知限制声明 + 参数约束 + 证伪记录 |
| **对 blueprint 的影响** | 标记 Phase 完成 | 回写参数约束、可能触发战略降级 |

### 3.5 从诊断到文档的反馈路径

旧模式中，诊断结论停留在 log.md 中，不自动反馈到 blueprint 和 downstream plan。新模式定义了按层级的反馈路径：

```
I 类确认 → 更新 YAML 模板和 config_reference.md
II 类确认 → 在父 plan 中追加「已知限制」→ 回写 blueprint 参数约束
III 类确认 → blueprint 标记诊断 Phase 完成 → 下游 plan 显式引用限制
IV 类确认 → blueprint 新增独立诊断 Phase → 回写所有 plan
V 类确认 → 修订 blueprint 战略目标 → 修订受影响的 plan
```

## 4. 控制论视角的深层分析

### 4.1 三种控制模态的协同

新框架中，问题应对不再是单一的反馈控制，而是三种模态的协同：

| 模态 | 在框架中的角色 | 时机 |
|------|------|------|
| **前馈控制** | Phase PRE 的参数约束、YAML 模板中的安全默认值、已知限制在 downstream plan 中的显式引用 | 在计算运行**之前**预防已知陷阱 |
| **诊断先验** | Phase 0A 的初始层级先验、偏差升级协议表中的历史频率、判别模板中的 D1 (利用已有数据) | 第一次看到症状时，用系统模型生成高效诊断序列 |
| **反馈控制** | Phase A–C 的参数矩阵扫描、判别实验的迭代执行 | 层级确定后，在对应层级内做参数优化或假设检验 |

**旧模式只有反馈控制**（看到问题 → 改参数 → 重跑），导致每次遇到相似问题时都从零开始。新框架将前馈（预防）和诊断先验（高效初诊）提升为与反馈同等的地位。

### 4.2 可观测性问题的工程解决

控制论中的可观测性问题（从输出无法唯一推断内部状态）在工程中通过**状态观测器**解决——使用系统模型 + 测量历史来估计不可直接测量的内部状态。

本框架中的**诊断先验**就是一种状态观测器：
- **系统模型** = `shared/tbplas-internals.md` 中的已知故障模式 + `kubo-bastin-convergence.md` 中的已知限制
- **测量历史** = `MG/docs/log.md` 中的历史故障条目 + 频率统计
- **状态估计** = Phase 0A 中的初始层级先验 $P(\text{I 类}) \approx 0.55$

这不是完美的观测器——先验可能错误（如 Nyquist 混叠不在初始假设空间中）——但它比纯直觉的猜测（"看起来像大问题"）要可靠得多。

### 4.3 反馈增益的层级适配

一个关键设计决策是：**不同层级的控制器应该有不同的增益**。

- **Level 1 控制器**：高增益——单次 NaN 就触发参数修正，成本低
- **Level 2 控制器**：中增益——需要 ≥3 个独立证据才触发新子 Phase
- **Level 3 控制器**：低增益——需要诊断 Phase 时间盒耗尽或 ≥3 个证伪实验才触发战略转向

旧模式的失败部分源于**增益错配**——σ_xy 基线偏移（Level 1 问题）触发了 Level 3 响应（quantum-kite 替代），即低层级偏差被大幅放大到高层级响应。新框架中的偏差升级协议通过显式的 I–V 分类来防止这种错配。

## 6. 应用示例：B=100T DOS/LDOS NaN 问题

当前 MG 项目正面临一个新问题：B=100T 下的 DOS 和 LDOS 计算输出全为 NaN，而 B=6/7/8T 正常。用新旧两种模式应对的对比：

### 旧模式 (直觉驱动)

```
"B=100T NaN 了 → 可能是 rescale 不够 → 改 rescale=20 试试 →
 不行 → 可能是 B 场实现有 bug → 去读 Peierls 代码 →
 找不到 bug → 算了先放一放"
```

### 新模式 (跨层级排除)

```
D1 [0 成本]: 确认 B=6/7/8T 正常 ✅
  → 排除 III (Peierls 代码 bug) + V (LDOS 在磁场下无 LL 的物理不可能)
  → 剩余: I (参数), II (收敛), IV (基础设施)

D2 [1 作业]: B=100T, rescale=20 (其余同)
  → 如果修复: I 类 (rescale 不足)，修正模板
  → 如果未修复: 排除 rescale

D3 [1 作业, 与 D2 并行]: B=50T, rescale=10 (其余同)
  → 找 NaN 的 B 阈值
  → 综合 D2+D3 可区分 rescale (I) vs 磁致带宽 (II)

D4 [如果 D2/D3 未修复]: B=100T, rescale=20, m=256
  → 如果正常: II 类 (收敛条件在大超胞下不满足)
  → 如果仍 NaN: 检查资源/基础设施 (IV)
```

**关键差异**：新模式不猜测"最可能的原因"然后去验证，而是设计一个序列，每步同时排除多个层级的可能性。D1 利用了已有数据（零成本），D2 和 D3 可以并行提交（节省墙钟时间）。

## 7. 核心教训

### 7.1 理论教训

1. **可观测性是诊断的根本瓶颈**：症状-根因之间的多对多映射使得纯直觉的层级判断不可靠。需要系统模型（先验）来正则化。
2. **递阶控制需要层级适配的增益**：低层级问题不应触发高层级响应。偏差升级协议通过显式分类来强制执行增益适配。
3. **前馈和诊断先验与反馈同等重要**：在复杂计算工作流中，预防（参数约束、已知限制传递）和高效初诊（跨层级排除模板）节省的时间远超反馈迭代。

### 7.2 实践教训

1. **默认参数必须进入假说矩阵**：案例 #1 的核心教训——如果 `num_integ_steps=2048` 作为一个假说被显式检验，10 天的诊断可以压缩到 1 天。
2. **诊断 Phase 必须有退出条件和时间盒**：Phase 3X 的持续膨胀说明缺少"何时停止寻找修复方案"的标准。
3. **I 类修复也必须文档化**：修复成本低不意味着不需要文档化。改一行 YAML 后不更新模板，下次还会发生。
4. **诊断结论必须显式传递到下游 plan**：Phase 3X 确认的 Γ·μ 限制应该在 Phase 4 plan 中作为"继承的已知限制"显式引用。

## 摘要

本文总结 `/home/wyl/.agents/skills/*/references/*.md` 中各模板的功能定位，形成「参考模型 → 状态观测器 → 执行清单」六文档体系；并针对"程序性与灵活性"的张力，提出基于**变更影响半径**的分级响应机制：小修改走局部反馈（直接改 + log 一句），大修改走全局前馈（先更新 plan 再分解 task）。核心判断是**控制代价 vs 控制收益**——流程强度应与变更影响半径成正比，而非一刀切。

## 1. 名称 + 一句话意图

**名称**：分级响应机制（变更影响半径决定流程强度）；其底层配套是**六文档体系**（参考模型 → 状态观测器 → 执行清单）。

**一句话意图**：判断一次变更的「影响半径」有多大，再按半径选择流程强度——小修改走局部反馈（直接改 + log 一句），大修改走全局前馈（先更新 plan 再分解 task），让流程强度与变更影响半径成正比，而非一刀切。

## 2. 触发条件（适用性）

翻这张卡的时机：项目里出现一次**代码/配置/文档变更**，需要判断"该走多重的流程"。判断阈值如下：

- **需要 task**：修改涉及 **≥ 2 个文件** 或 **需验证多个步骤** 或 **可能被遗忘**。
- **需要更新 plan**：修改会影响 **对外接口**（函数签名、YAML 键）、**数据格式**、**模块职责划分**，或 **未来需要追溯决策原因**。

直接回答三个"多大才算大"的问题：

> 修改一个小接口，是否有必要从 plan 层面修改，再新建一个 task？

- **如果只是改内部实现，签名不变** → 不需要 plan，但建议建一个 task（记录原因），或直接改 + log 记录。
- **如果修改了函数签名或 YAML 键** → 必须更新 plan（接口规范），再建 task 执行。

> 修改大到什么级别需要新建一个 task？

只要**不是单行 typo 级别**的修改，且**需要多步操作或验证**，就应建 task。task 是"最小可执行单元"，它保证你（或 AI）不会遗漏步骤，且后续可以追溯。

> 修改大到什么级别需要从 plan 开始大修？

当修改会**改变系统的外部可观测行为**（配置格式、输出格式、模块间依赖关系）时，就需要更新 plan。典型信号：你需要向别人解释"现在系统不同了" —— 那就说明 plan 该改了。

## 3. 系统建模 / 为何有效

分级响应的机制基础是**六文档体系**：项目使用六个文档分工协作，核心为"参考模型 → 状态观测器 → 执行清单"三文档体系。

| 文档 | 角色 | 类比 | 读者 | 更新频率 | 模板位置 |
|------|------|------|------|----------|----------|
| `CONTEXT.md` | 参考模型 — 项目"是什么" | 百科全书 | 🤖 AI | 低（架构变更时） | `run-task/references/context-template.md` |
| `STATUS.md` | 状态观测器 — 项目"怎么样了" | 仪表盘 | 👤 人类 | 高（每步完成时） | `run-task/references/status-template.md` |
| `docs/tasks.md` | 执行清单 — 具体"做什么" | 工作单 | 🤖+👤 双方 | 中（任务增删时） | `create-task/references/templates.md` |
| `README.md` | 用户手册 — 项目"怎么用" | 项目卡片 | 👤 用户 | 低 | `create-readme/references/template.md` |
| `docs/plan.md` | 技术设计 — 项目"怎么建" | 蓝图 | 👤 开发者 | 中（设计变更时） | `create-plan/references/template.md` |
| `docs/log.md` | 操作日志 — 项目"做了什么" | 航海日志 | 🤖+👤 | 高（每次操作后追加） | `run-task/references/log-template.md` |

（各文档的内容结构与更新职责分工见文末「附录」。）

**文档间关系图**：

```
CONTEXT.md (参考模型, 静态)
    ├── 链接 → STATUS.md (状态观测器, 动态)
    ├── 链接 → docs/tasks.md (执行清单)
    └── 引用 → README.md / docs/plan.md / docs/log.md

README.md (用户手册)
    └── 链接 → docs/plan.md (详细技术规格)

docs/plan.md (技术设计)
    └── 被 README.md 引用

docs/tasks.md (执行清单)
    └── 完成后 → 更新 STATUS.md + 追加 docs/log.md

docs/log.md (操作日志)
    └── 记录 tasks.md 中每条任务的执行结果
```

分级响应之所以有效，本质是**控制代价 vs 控制收益**：

- **小修改**：走流程的代价 > 收益 → 直接改 + 简单记录。
- **中修改**：流程代价 ≈ 收益 → 走轻量级 task。
- **大修改**：流程代价 < 收益（避免未来混乱）→ 走完整计划-任务-日志闭环。

**控制论视角**：
- 高频、低影响的扰动 → 使用**局部反馈**（直接修正）。
- 低频、高影响的变更 → 使用**全局前馈**（更新参考模型 plan，再分解执行）。

## 4. 规则 / 步骤

### 核心原则：基于变更的"影响半径"选择流程

| 变更类型 | 典型示例 | 是否需要更新 plan | 是否需要创建 task | 推荐操作 |
|----------|----------|-------------------|-------------------|----------|
| **微调** | 改一个魔法数字、修一个 typo、调整 plot 颜色 | ❌ | ❌ | 手动改 + `log.md` 记录一句话 |
| **局部修改** | 修改一个函数内部逻辑、增加一个辅助函数、改一个默认值 | ❌ | ✅ | 创建 task，AI 执行后更新 STATUS/log |
| **接口级修改** | 函数签名变化、新增 YAML 配置键、修改输出文件名格式 | ✅（更新 plan 接口规范） | ✅（拆解为 1~3 个 task） | 先更新 plan，再创建 task |
| **架构级修改** | 更换参数管理方式、增加新计算类型、重构模块间依赖 | ✅（大修 plan） | ✅（多个 task） | plan 评审 → 拆解任务 → 逐 task 执行 |

### 分级操作指南（结合已有文档体系）

#### 级别 0：不需要文档化的改动（"顺手改"）

- **场景**：修正拼写错误、调整一个常数值（如 `max_distance=0.75`→`0.8`）、增加一行注释、调整 plot 颜色。
- **操作**：直接在 VS Code 中修改，commit message 写清楚。`log.md` 可加一句"`2026-05-26: change max_distance to 0.8`"。
- **风险**：极低。

#### 级别 1：需要 task 但不动 plan（"局部调整"）

- **场景**：
  - 修复一个函数内的 bug（不改签名）。
  - 增加一个内部辅助函数。
  - 修改某个函数的默认参数值（签名不变）。
  - 调整输出文件保存路径（已在 plan 中约定过格式）。
- **操作**：
  1. 在 `tasks.md` 中添加一个任务（可使用 `create-task` skill）。
  2. 要求 AI 执行该任务。
  3. AI 执行后自动勾选 task，并在 `log.md` 追加执行记录，更新 `STATUS.md` 进度。
- **为什么不需要改 plan**：plan 记录的是**接口契约**和**架构设计**，这些修改不改变契约。

#### 级别 2：需要 task + 局部更新 plan（"接口微调"）

- **场景**：
  - 给一个现有函数增加一个新参数（带默认值），不影响旧调用。
  - YAML 配置中增加一个可选键（有默认值）。
  - 输出文件增加一列（但保持向后兼容）。
- **操作**：
  1. 在 `plan.md` 的"接口规范"或"参数设计表"中更新相应条目。
  2. 在 `tasks.md` 中创建任务："更新 `calc.py` 中的 `calc_dos_tbpm` 函数，增加 `use_cache` 参数，默认 False"。
  3. AI 执行并更新 log/STATUS。
- **为什么需要更新 plan**：plan 是接口的权威来源，保持与代码同步才能发挥"参考模型"的作用。

#### 级别 3：需要大修 plan + 多个 task（"架构演进"）

- **场景**：
  - 改变参数管理方式（如从 YAML 切回 argparse，或改用 Pydantic）。
  - 拆分/合并模块（如把 `io_vis.py` 拆成 `io.py` 和 `vis.py`）。
  - 增加全新的计算类型（如 `transport`）。
- **操作**：
  1. 先修改 `plan.md` 的相应章节（架构图、模块划分、接口规范）。
  2. 在 `tasks.md` 中创建多个子任务，覆盖代码修改、测试、文档更新。
  3. 按序执行，每个子任务完成后更新 STATUS/log。
- **建议**：大修前先在 `log.md` 中记录决策背景（为什么改），便于日后回溯。

## 5. 反例与失效模式（禁忌）

这张卡要避免两个失效模式，分级响应机制正是为此而设：

> 程序性与灵活性并非对立，而是**不同规模变更下的最优控制策略**。一刀切的流程会扼杀效率，但完全无序的临时修改会导致技术债务累积。关键是建立**分级响应机制**。

- **失效模式一：一刀切（过度流程化）**——对所有变更都套用完整流程，扼杀效率。
- **失效模式二：完全无序（欠流程化）**——所有变更都临时手动改、不记录，导致技术债务累积。

两种失效的根源都是**流程强度与变更影响半径脱钩**；分级响应就是把强度重新挂钩到半径上。

**边界**：级别 0 的"顺手改"（改 typo、调常量）明确**不需要** task/plan 流程——此时若过度流程化（为一句 log 该不该记而建 task），本身即属失效模式一。

## 7. 速查表

**口诀**（可放进 `CONTEXT.md` 的"AI 工作流指引"）：

> **一行改，log 记；
> 多步改，task 立；
> 接口变，plan 更；
> 架构动，先讨论。**

**快速判断"修改有多大" checklist**：

| 问题 | 是 → 级别 | 否 → 继续判断 |
|------|----------|--------------|
| 修改后是否会改变已有脚本的运行方式（如命令行参数、YAML 键名）？ | 至少级别 2 | 往下 |
| 修改是否涉及多个函数/文件，且需要分步验证？ | 级别 1 | 往下 |
| 修改是否只是单行/单文件内的 trivial 改动？ | 级别 0 | — |

**额外规则**：
- 如果改完自己 **3 天后可能忘记为什么这么改**，就应该记入 `log.md`（至少一句话）。
- 如果改完会影响 **协作者或未来的自己如何理解系统**，就应该更新 `plan.md`。

（口诀说明：把这句话放在 `CONTEXT.md` 的"AI 工作流指引"中，让 AI 也遵循这套分级规则。这样既保持了日常开发的灵活性，又确保了关键决策的可追溯性。）

### 1. CONTEXT.md — AI 对话入口（参考模型）

**模板路径**: `run-task/references/context-template.md`

**功能定位**: 为 AI 提供项目的**永久有效静态信息**，是 AI 每次对话的入口参考。AI 通过节名定位获取项目约定、环境配置、文件速查等。

**内容结构**:

| 节名 | 用途 | 是否自动更新 |
|------|------|-------------|
| `## 项目身份` | 环境、语言、入口命令 | 否（项目初始化时填入） |
| `## 当前进度` | 链接引用 STATUS.md + tasks.md | 否（静态文本） |
| `## 关键文件速查` | Markdown 表格，列: `想看什么`、`读哪个文件` | 否（架构变更时手动更新） |
| `## AI 工作流指引` | Markdown 表格，列: `你被要求做什么`、`你应该读什么` | 否（项目初期设定） |
| `## 项目约定` | Markdown 表格，列: `约定项`、`说明` | 否（约定变更时手动更新） |
| `## 已知注意事项` | 无序列表，每行一条 | **是**（发现新注意事项时追加） |

**核心约束**:
- 总长度控制在 **~80 行以内**
- 进度/任务状态**不**放在此文件，统一由 STATUS.md 管理
- 通过链接引用 STATUS.md 获取最新进度，不重复维护
- 注意事项追加到列表末尾，不删除已有条目

### 2. README.md — 用户手册（项目卡片）

**模板路径**: `create-readme/references/template.md`

**功能定位**: 面向**用户**（含未来的自己）的快速入门手册，回答"项目能做什么、怎么快速跑起来"。

**内容结构**:

| 节名 | 内容 |
|------|------|
| 快速启动 | conda 环境激活、本地运行命令、SLURM 提交命令 |
| 依赖 | 核心依赖库列表及说明 |
| 物理/业务内容 | 系统模型描述、计算量表格、研究目标 |
| 计算方法 | Mermaid 流程图、链接到 plan.md 获取详细接口 |
| 参数设置 | YAML 配置文件示例、参数含义说明 |
| 输出结构 | 项目目录树、数据文件命名示例 |
| 使用方式 | 交互运行 / MPI 并行 / SLURM 集群提交 |
| 当前状态摘要 | 已完成的计算维度表格 |
| 后续计划 | 里程碑 checklist，链接到 plan.md |
| 参考文献 | 标准文献引用 |

**与 plan.md 的职责分离**: README.md 侧重"怎么用"，plan.md 侧重"怎么建"，两者通过链接互相引用。

### 3. STATUS.md — 项目状态看板（状态观测器）

**模板路径**: `run-task/references/status-template.md`

**功能定位**: 人类可读的**动态进度看板**，由人类维护进度、AI 完成任务后更新。CONTEXT.md 通过链接引用此文件。

**内容结构**:

| 节名 | 用途 | 是否自动更新 |
|------|------|-------------|
| `## 当前阶段` | 阶段名称 + 最后操作时间、已完成/进行中/阻塞 | **是**（每任务完成后） |
| `## 最近三次决策/发现` | 最多 3 条，最新在前，每条 ≤15 字 | **是**（每任务完成后插入） |
| `## 下一步（明确可执行）` | 可执行的下一步行动 checklist | 按需 |
| `## 指标健康度` | 进度百分比、代码质量、集群连通性、文档同步 | 按需 |
| `## 当前主要目标（月/周）` | 中长期目标 + checkbox | 仅关联时更新 |

**task-runner 更新规则**:
1. 更新 `当前阶段 > 最后操作时间` 为当前时刻
2. 在 `已完成` 末尾追加 ` + <任务摘要>`
3. 任务完成后 `进行中` 写 `无阻塞`
4. 将任务摘要插到 `最近三次决策/发现` 最前面作为第 1 条，保留 3 条

**约束**: 不放项目结构/环境配置（属 CONTEXT.md），不放具体执行步骤（属 tasks.md），每次会话结束前更新。

### 4. docs/plan.md — 技术设计计划书（蓝图）

**模板路径**: `create-plan/references/template.md`

**功能定位**: 面向**开发者**的前期技术设计文档，在写代码之前明确项目如何构建。使用计划性语言（"计划签名"、"规划描述"、"设计表"）。

**内容结构**:

| 节名 | 内容 |
|------|------|
| 项目概述 | 项目背景、物理图景、研究目标 |
| 计算步骤 | 按顺序列出：环境配置→模型构建→原子弛豫→模型后处理→物理量计算→数据保存与可视化 |

### 5. docs/tasks.md — 任务执行清单（工作单）

**模板路径**: `create-task/references/templates.md`

**功能定位**: 可执行的**具体任务条目**，AI 和人类双方共同使用。每个任务包含 7 要素，确保可独立执行和验证。

**条目模板结构**:

```markdown
### [ ] YL: MMDD_HHMM - 标题（≤15字）

**目标**: 1-2 句，要达成什么
**背景**: （可选）为什么做
**输入**: 数据路径、参考代码位置
**执行步骤**: 每步一个可执行的操作（命令完整，参数具体）
**约束**: 不修改文件列表、环境要求
**预期输出**: 输出文件路径、格式描述
**成功判据**: 可客观验证的 checklist
```

**文档结构**: 分为 `## 未完成` 和 `## 已完成` 两大区域，任务完成后从"未完成"移至"已完成"。

### 6. docs/log.md — 操作日志（航海日志）

**模板路径**: `run-task/references/log-template.md`

**功能定位**: 记录人类（YL）和 AI 的**每次操作和变更**，采用追加模式，永不完全重写。按时间戳组织，人类和 AI 各有标准格式。

**条目格式**:

#### AI 条目格式
```markdown
## AI: MMDD_HHMM - 简短摘要（5-10字）

[一段话概述完成了什么]

**涉及文件**：
| 文件 | 函数 | 旧接口 | 新接口 |
|------|------|--------|--------|

**配置变更**（如有）：diff 风格 YAML 展示
```

#### 关键规则
1. **时间戳**: `MM-DD HH:MM` 格式
2. **仅追加**: 在 log.md 末尾追加，保留空行分隔
3. **不删除旧内容**: 永远不删除或改写已有 YL/AI 条目
4. **涉及文件表格**: 每个修改的函数一行
5. **配置变更**: 仅 YAML/JSON 有变时才添加

**代码参考**: 提供 `find_yl_entry()` 和 `append_ai_entry()` 两个辅助函数，用于程序化读写日志。

# 案例研究: 多会话并发编辑 — 共享资源竞争与状态同步协议

> **领域标签**: 系统科学 · 控制论 · 并发控制 · 协议设计 · 人机协作
> **时间跨度**: 2026-07-19 ~ 2026-07-21
> **相关项目**: `/home/wyl/project/MG/` (multilayer graphene QHE)
> **关联案例**:
>   - `03_case_study_problem_response_workflow.md` — 偏差升级协议（本案例解决的正是该协议中「Planning 会话如何获知 Execution 会话的发现」的信息传递问题）
>   - `04_case_study_tianshui_lead_response.md` — 天水血铅（同样的层级误判 → 过度响应模式在文件系统中的再现：Execution 会话对 plan.md 做了超出其权限的结构性编辑）
> **核心协议**: `/memories/session-handoff.md`（会话交接协议）, `MG/STATUS.md`（交接条存放位置）
> **涉及 SKILL**: `create-blueprint`, `create-plan`, `run-task`, `debug-workflow`

## 摘要

在 MG 项目的多层石墨烯量子霍尔效应计算中，研究工作流被分解为三个角色：Planning 会话（设计 plan 结构）、Execution 会话（执行 tasks 并记录结果）、Research 会话（跨工作区调整战略）。三个角色分别运行在独立的 AI 会话中，但它们共享同一组文件——`plan.md`、`tasks.md`、`blue_print.md`、`STATUS.md`。

这构成了一个经典的**共享资源竞争**问题。2026 年 7 月，R04 Phase D 的 B 场下 LDOS 计算遇到收敛问题时，Execution 会话在 `tasks.md` 中插入了 D1b-D1e 四个诊断子任务，但 `plan.md` 的 Phase D 结构未被同步更新。当用户切回 Planning 会话后，Planning 按旧的 `plan.md` 结构编辑并写回——覆盖了 Execution 会话存在的事实。D1b-D1e 的内容虽然在 `tasks.md` 中幸存，但它们与 `plan.md` 的结构性断裂使得下一次 Planning 编辑必然产生冲突。

本文以控制论的**共享资源竞争**、**状态可观测性**和**控制器增益适配**为分析框架，追溯了该问题的发现过程，记录了会话交接协议的四个迭代版本（git → session memory → `_handoff.md` → `STATUS.md`），并分析了每个版本被否决或被采纳的系统性原因。最终方案——将交接条嵌入 `STATUS.md` 的「待 Planning 会话处理」节——是**最小侵入性、最大可见性、零新文件**的帕累托最优解。

## 1. 系统建模：三个控制器共享一个执行器

### 1.1 拓扑结构

```
┌──────────────────┐     ┌──────────────────┐     ┌──────────────────┐
│ Research 会话    │     │ Planning 会话    │     │ Execution 会话   │
│ (战略控制器)     │     │ (结构控制器)     │     │ (操作控制器)     │
│ 工作区: Research │     │ 工作区: MG       │     │ 工作区: MG       │
└────────┬─────────┘     └────────┬─────────┘     └────────┬─────────┘
         │                        │                        │
         │   编辑 blue_print      │   编辑 plan            │   编辑 tasks/log
         │                        │                        │
         ▼                        ▼                        ▼
┌──────────────────────────────────────────────────────────────────┐
│                        文件系统 (共享执行器)                      │
│  blue_print.md  │  plan.md  │  tasks.md  │  STATUS.md  │  log.md │
└──────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- 三个控制器**彼此不知道对方的存在**——没有跨会话的状态同步信道
- 共享执行器（文件系统）**没有互斥锁**——任何控制器可以在任何时间写入任何文件
- 每个控制器持有自己**最后一次读取的文件内存副本**——副本可能已过期

### 1.2 可观测性分析

在控制论中，一个控制器要做出正确决策，需要**观测**到系统的当前状态。本系统中：

| 状态变量 | 对 Planning 可观测？ | 对 Execution 可观测？ |
|------|:---:|:---:|
| `plan.md` 是否被另一会话修改过 | ❌ 不可观测 | ❌ 不可观测 |
| `tasks.md` 是否新增了需要 plan 结构响应的任务 | ❌ 不可观测 | ✅ 可观测（自身修改的） |
| `blue_print.md` 是否被 Research 会话更新 | ❌ 不可观测 | ❌ 不可观测 |

**可观测性矩阵是奇异的**——没有任何一个控制器能观测到其他控制器对共享文件的修改。这是并发冲突的根本原因。

### 1.3 与 93 号案例（偏差升级协议）的接口缺口

93 号案例定义了五类偏差（I–V）及其对应的响应层级和文档修订路径。但它隐含地假设了一个前提：**发现偏差的会话和负责修订文档的会话之间有信息传递信道**。

实际情况是：这个信道不存在。Execution 会话发现 III 类偏差（Chebyshev 噪声放大 LDOS 振幅 2-5×），知道这需要写入 plan 的「已知限制」——但它没有渠道把这个信息传递给 Planning 会话。这是 93 号案例的协议设计中未被覆盖的**信息传递层**。

## 2. 故障实例：R04 Phase D 的 D1b-D1e 断裂

### 2.1 事件序列

```
T1: Planning 会话写入 plan.md (Phase D = D.1 → D.2 → D.3 → D.4 → D.5)
T2: Execution 会话读取 plan.md (拿到 T1 版本)
T3: Execution 会话在 tasks.md 中新增 D1b, D1c, D1d, D1e
    （正确——tasks 是 Execution 专属）
T4: Execution 会话未通知 Planning（没有写交接条）
T5: 用户切换到 Planning 会话
T6: Planning 会话的内存中仍是 T1 版本的 plan.md
T7: Planning 编辑 plan.md → 写回 → 覆盖了磁盘上的任何中间变更
    （实际上 plan.md 在 T3-T6 之间未被 Execution 修改——因为 Execution 正确地
     没有直接编辑 plan.md。但断裂在于：plan.md 的 Phase D 仍然是 D.1-D.5
     的线性结构，而 tasks.md 已经变成了 D.1 → D1b-D1e → D.2-D.5。）
T8: 两个文件之间出现结构性不一致：tasks 描述了 plan 中不存在的子 Phase
```

### 2.2 断裂的本质

这不是传统意义上的「文件被覆盖」——`plan.md` 的字节确实没有被覆盖。**断裂是语义层的**：`plan.md` 声称 Phase D 有 5 个子步骤，`tasks.md` 声称 Phase D 有 8 个子步骤。Planning 会话下次编辑 `plan.md` 时，如果只读 `plan.md` 而不读 `tasks.md`，它将基于一个不完整的结构模型做决策。

### 2.3 控制论诊断

| 故障点 | 控制论概念 | 具体表现 |
|------|------|------|
| T4 缺失 | **前馈路径断裂** | Execution 发现结构变更需求但未传递给 Planning |
| T6 过期副本 | **状态观测延迟** | Planning 持有的 plan.md 内存副本仍是 T1 版本 |
| T7 正常写入 | **无互斥协议** | 文件系统没有阻止基于过期副本的写入 |
| T8 不一致 | **模型-现实分歧** | plan.md 和 tasks.md 对同一 Phase 的结构描述出现分歧 |

## 3. 解决方案的四次迭代

### 3.1 v1: Git 方案（被否决）

**设计**：每次编辑前 `git pull`，编辑后 `git commit + push`。

**否决原因**：
- **增益过高**：编辑频率是分钟级，冲突实际只在会话切换时发生。git 的 commit/push 开销远大于问题的实际规模。
- **粒度不匹配**：git 管理的是代码版本，交接需要的是「我上次离开后，另一个我改了什么东西」的瞬态认知同步。
- **适用场景错位**：git 为多人多机设计。单人单机场景下，两个会话的「并发」本质上是串行的——你不会同时在两个会话里打字——只是编辑间隙中另一个会话不知道你改了什么。

### 3.2 v2: `/memories/session/` 方案（被否决）

**设计**：Execution 会话在 `/memories/session/` 下创建 `handoff_*.md` 文件；Planning 会话启动时检查该目录。

**否决原因**：
- **用户不可见**：`/memories/session/` 是 AI 的内部存储，在文件管理器中不显示。用户无法直接查看、编辑或确认交接条的存在。交接协议的双方是人（你切换会话时的不同意图），不是 AI——交接条必须对**你**可见。
- **生命周期管理困难**：处理完的交接条需要显式删除，但用户看不到它们，只能依赖 AI 记得删除。

**保留的有效部分**：`/memories/session-handoff.md` 作为协议规则文档保留——它是静态的协议规则，适合放在始终自动加载的用户记忆中。

### 3.3 v3: `docs/_handoff.md` 方案（部分采纳）

**设计**：在 MG 项目 `docs/` 下创建 `_handoff.md` 作为交接条专用文件。

**优点**：对用户可见（文件列表中直接看到）；可直接编辑。

**被优化的原因**：引入了新文件。MG 项目中已经有一个文件在做交接条的半份工作——`STATUS.md` 的「阻塞」「最近三次决策/发现」「下一步」等节本质上就是交接信息。与其新建一个文件做完全一样的事，不如把这个已有的半份工作完善成全份。

### 3.4 v4: `STATUS.md` 方案（✅ 采纳）

**设计**：在 `STATUS.md` 中新增「📋 待 Planning 会话处理」节。Execution 会话在此节追加待处理条目；Planning 会话编辑 plan/blueprint 前先读取此节并处理；处理完勾 `[x]` 或移入「已完成」。

**采纳原因**——满足全部五个约束：

| 约束 | 满足方式 |
|------|------|
| **对用户可见** | `STATUS.md` 是项目状态看板，每次打开就能看到 |
| **AI 可自动读取** | `STATUS.md` 已在 `CONTEXT.md` 引用中，「待处理」节的位置固定 |
| **零新文件** | 复用已有基础设施，无架构膨胀 |
| **生命周期自管理** | 与 `STATUS.md` 的其他条目共享 `[ ]` → `[x]` → 移入已完成的流程 |
| **跨工作区可达** | 绝对路径 `/home/wyl/project/MG/STATUS.md`，任何工作区的会话都能 `read_file` |

### 3.5 配套的控制器纪律

仅有一个交接节不够——还需要约束控制器行为以防止在交接完成前产生冲突：

**编辑前纪律**（嵌入 `create-blueprint`、`create-plan` 的 Procedure §1 和 `run-task` 的 §3）：
```
1. 读取 STATUS.md「📋 待 Planning 会话处理」节
2. read_file 重读目标文件（获取最新版本）
3. 再开始编辑
```

**角色权限纪律**（嵌入 `/memories/session-handoff.md` 用户记忆）：
- Execution 会话**不直接编辑 plan.md / blue_print.md 的结构**
- 需要结构变更时 → 在 STATUS 写交接条目 → Planning 执行
- Execution 可自由编辑 tasks.md（自身专属）和 log.md（自身专属）

## 4. 控制论视角的深层分析

### 4.1 从共享资源竞争到状态同步协议

经典并发控制（如数据库的 2PL、MVCC）依赖一个**中心化的锁管理器**。在本系统中，没有这样的中心化组件——AI 会话是独立的进程，文件系统是无状态的。

会话交接协议本质上是实现了一个**去中心化的乐观并发控制**：

```
经典乐观并发控制:
  1. 读取数据 + 版本号
  2. 本地修改
  3. 提交时检查版本号 → 如果版本号变了，冲突，重试

会话交接协议:
  1. 读取 STATUS 交接节 + 目标文件
  2. 本地修改
  3. 写回
  4. 写入方在 STATUS 中追加交接条目（通知其他控制器）
  5. 其他控制器在编辑前检查 STATUS（冲突检测前移到了编辑前）
```

关键差异：冲突检测从「提交时」前移到了「编辑前」。这不是性能优化，而是**人的认知节奏适配**——你在编辑前需要知道「有没有我漏掉的信息」，而不是在编辑后被 git merge conflict 打断。

### 4.2 四个迭代版本的设计空间探索

从控制论角度看，四个版本在探索同一个设计空间——**状态同步信道的三个维度**：

| 版本 | 信道位置 | 用户可见性 | 架构侵入性 |
|------|:---:|:---:|:---:|
| git | 版本控制系统（外部） | ✅ | 🔴 高（需要 commit/push/pull 纪律） |
| session memory | AI 内部存储 | ❌ | 🟢 低 |
| `_handoff.md` | 项目文件系统（新文件） | ✅ | 🟡 中（引入新文件类型） |
| `STATUS.md` | 项目文件系统（复用） | ✅ | 🟢 最低（修改已有节） |

v4 是帕累托最优：它在三个维度上都不差于其他版本，且在「架构侵入性」上严格优于 v1 和 v3。

### 4.3 控制器增益的层级适配

交接协议的核心洞察——Execution 不直接编辑 plan 结构——可以用增益理论重新表述：

**Execution 会话的控制器增益应限制在 Level 1（操作层）**。它在 tasks.md 中新增任务、更新状态、在 log.md 中记录结果——这些都是低增益操作，影响范围局限于自身专属文件。

**当 Execution 试图编辑 plan.md 的结构时，它在用 Level 1 的控制器做出 Level 2 的响应**——这是增益错配。正确的做法是：Execution 将「需要 Level 2 响应」的信号（交接条）传递给 Planning，由 Planning——这个被设计为 Level 2 增益的控制器——来执行结构变更。

这是 93 号案例的偏差升级协议在本案例中的精确应用：**不是不能响应，而是在正确的层级响应**。

## 6. 核心教训

### 6.1 理论教训

1. **可观测性不止是传感器的问题，也是协议的问题**。三个控制器都可以技术上 `read_file` 获取最新状态——可观测性失败不是因为传感器缺失，而是因为没有协议规定**何时应该读取**。编辑前纪律解决了这个问题。

2. **去中心化并发控制不需要锁**。乐观并发控制 + 冲突检测前移（编辑前检查交接节）在控制器数量少（3 个）、写入频率低（分钟级）的场景下足够有效，且避免了中心化锁管理器的架构复杂性。

3. **交接条的位置选择是信息架构问题**。每多一个文件就是每多一份维护负担。解决方案应该优先复用已有基础设施——STATUS 已经在做交接条的半份工作，完善的成本远低于新建。

### 6.2 实践教训

1. **协议必须对人可见**。AI 之间的自动交接（session memory）听起来高效，但实际上交接的双方是你——是你切换会话时的意图变化，不是 AI 的背景进程。交接条必须放在你能看到、能手动编辑、能确认已处理的位置。

2. **控制器角色必须硬编码到协议中**。「Execution 不直接改 plan 结构」不是建议，是纪律。这个约束必须同时存在于用户记忆（自动加载）和 SKILL 检查点（执行前强制）。

3. **设计迭代的否决理由本身就是知识**。v1（git）被否决因为增益过高，v2（session memory）被否决因为用户不可见——这两个否决理由不是失败的痕迹，而是**对约束空间的认识深化**。它们应该在协议文档中被保留，供未来的协议修订参考。

## QA-002: 委托执行中，管理者如何控制执行者上报信息的准确性？（2026-08-19）

### 用户问题（原文）

> 从控制论和管理学的角度看, 当管理者无法亲自执行每一项具体工作时, 具体工作需要委托给执行人执行, 这个执行人可能是人类也可能是 AI agent, 管理者如何控制执行者上报的信息的准确性?

### 回答概要

将管理者-执行者系统建模为分层控制系统：**信息上行通道与验证通道必须分离**（巡视制度/上访制度的职能）。核心原则是**验证成本的不对称**——让执行者出错的成本远高于管理者抽查的成本。五个机制：

1. **可验证证据格式**：每条上报附出处证明，裸结论不可审计；
2. **原始信源旁路**：审计直接对原始信源比对，不经执行者转述；
3. **抽样审计 + 威慑**：不全查，但抽中即重罚；
4. **风险显性化**：强制标注不确定（📊F/💭I），"错在明处"而非隐藏；
5. **负反馈闭环**：错误回流为规范，系统持续收敛。

失效信号：上报越来越流畅却无出处；同类错误重复出现（反馈断了）；执行者猜测管理者意图（激励错位）；验证成本回升（格式退化）。

完整案例见 `case/09_case_study_delegation_accuracy_control.md`；对 AI agent 与人类下属通用；落地实例为 `research_onboarding_skill` v1.3 的 LITERATURE_QC_PROTOCOL。

## 0. 为什么这个案例恰好是控制论/系统工程的活教材

你的 Kubo-Bastin QHE 调试经历，如果翻译成控制论的语言，就是：

> 一个高维非线性动力学系统（Chebyshev 展开 + Kubo 公式数值积分）在某些运行条件下（能量参数 E）稳定（→ 正确的 $\sigma_{xy} = \pm 2 e^2/h$），在另一些条件下不稳定（→ 发散 → NaN）。你作为"系统操作员"，通过一系列诊断实验（参数扫描、根因假设、对照测试），逐步识别出系统的稳定边界和失稳机制。

这段经历完美覆盖了系统科学的四个核心概念：
1. **系统辨识**：从"不清楚为什么会 NaN"到"搞清楚不同 E 区域的不同行为"
2. **稳定性分析**：不同能量窗口对应不同的"模态稳定性"
3. **反馈诊断**：假设 → 测试 → 观察 → 修正假设的闭环
4. **系统工程**：配置管理、参数空间探索、失败模式的形式化

## 1. 系统模型：Kubo-Bastin 计算作为一个动力学系统

### 1.1 状态空间表示

Kubo-Bastin Hall 电导率的数值计算可以抽象为一个离散时间动力学系统：

$$\mathbf{x}_{n+1} = T_M \cdot \mathbf{x}_n$$

其中：
- $\mathbf{x}_n$ 是第 $n$ 阶 Chebyshev 展开系数向量
- $T_M$ 是 Chebyshev 递推算子（依赖于 $M$ = `dckb_num_kernel`）
- 输出 $\sigma_{xy}(E) = \mathbf{c}^T \cdot \mathbf{x}(E)$

**系统矩阵** $T_M$ 在 double 精度下的关键性质：
- 理论上：Chebyshev 多项式 $T_n(x)$ 在 $[-1,1]$ 上正交，递推 $T_{n+1} = 2xT_n - T_{n-1}$ 稳定
- 实际上：$M > 512$ 时，舍入误差累积导致正交性丢失 → $T_M$ 的有效条件数指数增长

### 1.2 "能量 E 作为系统参数"——模态分析视角

这是你最关键的发现。不同能量 $E$ 下的行为不同，翻译成控制论就是：

> 系统矩阵 $T_M(E)$ 是能量依赖的。对于不同 $E$，系统的**模态**（eigenmodes）有不同的稳定性。

具体地：
- **Dirac cone 附近**（$E \approx 0$）：Chebyshev 展开的核函数在此处变化平缓，展开系数快速衰减，舍入误差贡献小 → **稳定模态**
- **远离 Dirac cone**（$|E| > 0.5$ eV）：展开系数衰减慢，高阶项贡献大，舍入误差在高阶递推中累积 → **不稳定模态**
- **极端能量**：展开系数几乎不衰减 → 高阶项噪声主导 → NaN

这就像一个飞机在不同飞行包线内的稳定性不同——低速时稳定，跨音速时可能失稳（颤振）。控制工程师用**根轨迹**或**极点图**来看这个，你的 M 扫描本质上就是计算系统的"极点分布随参数变化"。

## 2. 调试过程重新叙述：一个渐进式系统辨识故事

### 2.1 第一阶段：症状识别（"全 NaN" = 系统完全失稳）

**观测**：$\sigma_{xy}(E)$ 对所有 500 个能量点全返回 NaN。

**控制论翻译**：输出信号 $y(t) = \text{NaN}, \forall t$。系统完全失稳。可能原因：
- 输入信号超出有效范围（rescale 问题 → 输入饱和）
- 系统内部状态发散（Chebyshev 递推发散 → 内部不稳定）
- 两者兼有

这就是系统辨识中的**故障检测与隔离**（Fault Detection and Isolation, FDI）问题——多个故障模式有重叠的症状。

### 2.2 第二阶段：竞争假设（"rescale 问题" vs "Chebyshev 发散"）

**你的 AI 助手给出了两个互斥的诊断**——有时认为是 rescale，有时认为是 Chebyshev 发散。

**控制论翻译**：这是**模型选择**（model selection）或**假设检验**问题。你有两个候选模型：

| 候选模型 | 故障机制 | 预测 |
|---------|---------|------|
| $H_1$: rescale 错误 | 输入信号超出 Chebyshev 核的 $[-1,1]$ 定义域 | 调整 rescale 应能修复 |
| $H_2$: Chebyshev 发散 | 递推中正交性丢失，噪声指数增长 | 降低 M 应该改善 |

**为什么 AI 在不同时刻给出不同诊断？** 因为在缺乏充分实验数据的条件下，两个模型都能"解释"全 NaN 的症状——它们在观测上**不可区分**。这是系统辨识中经典的**可辨识性**（identifiability）问题：仅凭"全 NaN"这个单一观测，无法区分这两个故障模式。

### 2.3 第三阶段：设计判别实验（M 扫描测试计划）

你做了正确的事——设计了**判别实验**（discriminating experiment）：

**控制论翻译**：你固定其他参数不变，单独扫描 $M$（`dckb_num_kernel`），这相当于对系统施加一个**参数扫描输入**，观察输出的频率响应。

如果 $H_1$（rescale）是对的 → 改变 M 不应该改变 NaN 的基本行为模式（NaN 要么全有要么全无）。

如果 $H_2$（Chebyshev 发散）是对的 → 增大 M 应该使发散更严重，减小 M 应该改善。

### 2.4 第四阶段：意外发现（"Dirac cone 附近收敛了！"）

**实验结果**：

| M | 预期（$H_2$ 简单版） | 实测 |
|:---:|------|------|
| 64 | 信号弱 | 信号弱，全窗口 RMS=0.246 |
| 256 | 信号浮现 | 信号浮现，RMS=2.776 |
| 512 | 噪声增长 | 噪声增长，RMS=8.690 |
| 1024 | 全 NaN | **无 NaN！** RMS=24.454，线性增长 |

而且最关键的是：**Dirac cone 附近的 $\sigma_{xy}$ 在 M=256 时就明确显示出量化趋势（→ ±2 e²/h），而远离 Dirac cone 的能量则发散**。

**控制论翻译**：这是诊断的突破口——你发现了系统不是"全局稳定或不稳定"，而是**模态选择性稳定**。这在控制论中被称为**选择性模态失稳**（selective mode instability）：系统的某些模态（Dirac cone 对应的 Chebyshev 展开模式）在高 M 下保持稳定，而其他模态发散。

这推翻了 $H_1$（rescale 是全局参数，如果是 rescale 问题，所有 E 应该同时受影响）和简单的 $H_2$（"M 越大越差"太粗糙——Dirac cone 在 M=1024 时反而最清晰）。

**正确的诊断是**：$H_2$ 的精细化版本——"Chebyshev 递推的稳定性是**能量依赖**的"。不同能量窗口有不同的有效噪声放大因子。

## 3. 这个案例教给我们的系统工程教训

### 3.1 教训一：计算 pipeline 是系统，需要稳定性分析

你不只是"跑了一个计算"，你是在运行一个**有内部状态的动力学系统**。任何数值方法（KPM、SCF、MD、MC）都有：
- **稳定运行包线**（stable operating envelope）：参数空间中可以安全运行的区域
- **失稳模式**（failure modes）：参数超出包线后如何失稳
- **模态结构**（modal structure）：系统中哪些"方向"（能量窗、k 点、样本）更脆弱

系统工程的思维是：**在跑计算之前，先知道你的系统在参数空间的哪些区域是稳定的**。就像飞机有飞行包线图，计算 pipeline 也应该有"稳定包线图"。

### 3.2 教训二：可辨识性——为什么"全 NaN"不足以诊断

你经历的核心困境——两个模型都能解释同一症状——是系统辨识中的经典问题：

> 仅凭故障症状（全 NaN），无法区分"输入问题"和"内部动力学问题"。

解决方案是**设计判别实验**——你做的 M 扫描就是教科书级的判别实验。你找到了一个参数（M），它对两个假设的预测不同：
- $H_1$ 预测：改变 M 不影响 NaN 模式
- $H_2$ 预测：改变 M 改变发散的严重程度

当实验结果既不完全支持 $H_1$ 也不完全支持简单 $H_2$ 时，你发现了更精细的真相：**模态依赖的稳定性**。这个过程——假设 → 判别实验 → 结果推翻假设 → 精细化假设——就是科学方法和系统工程方法的共同核心。

### 3.3 教训三：你的"诊断工作流"已经是反馈控制系统

回顾你做的事情：

```text
观测（全 NaN）
    ↓
假设生成（rescale? Chebyshev?）
    ↓
设计实验（M 扫描计划）
    ↓
执行实验（提交 8 个 SLURM 作业）
    ↓
观测结果（Dirac cone 收敛，其余发散）
    ↓
更新模型（模态依赖稳定性）
    ↓
新的假设 → ...（循环继续）
```

这在控制论中就是**参数估计 + 自适应控制的闭环**。你的大脑是这个回路中的"控制器"——根据误差（观测与预期的差异）调整对系统的理解（内部模型），然后设计新的探测动作。

### 3.4 教训四：配置管理的系统工程价值

你在这次调试中产生的大量 YAML 文件、SLURM 脚本、分析脚本和分析结果，如果没有好的配置管理，会迅速失控。系统工程中的**配置管理**（Configuration Management）和**需求追踪**（Requirements Traceability）正是为这个设计的：

```
hall_M064.yaml  →  job 283022  →  hall_AB_d0.000_M064_B100.0.txt  →  RMS=0.246
hall_M128.yaml  →  job 283023  →  hall_AB_d0.000_M128_B100.0.txt  →  RMS=0.246
...
```

每一条链路都可追溯——这是系统工程 V&V（验证与确认）的精髓。

## 4. 将系统科学原则操作化：计算物理调试 checklist

基于这个案例，以下是一个可以反复使用的**系统化调试框架**（结合控制论 + 系统工程）：

### Phase A: 故障表征（Fault Characterization）
- [ ] **症状是什么？** 全 NaN？部分 NaN？数值噪声？定性错误？
- [ ] **症状是全局的还是局部的？** 所有参数组合都出问题，还是某些参数？
- [ ] **症状的时间/迭代演化是什么样的？** 立即 NaN？逐渐发散？震荡？

### Phase B: 系统建模（System Modeling）
- [ ] 把计算 pipeline 画成**信号流图**：输入 → 处理 → 中间状态 → 输出
- [ ] 标注每一步可能的**故障注入点**（rescale 在输入端，正交性丢失在递推中，精度在累积处）
- [ ] 为每个故障模式写出**可测试的预测**

### Phase C: 判别实验设计（Discriminating Experiment Design）
- [ ] 找到能区分竞争假设的**控制参数**（如 M 之于 rescale vs Chebyshev）
- [ ] 设计**最小参数扫描**（最少实验次数来拒绝一个假设）
- [ ] 预设**证伪条件**：如果看到 X，$H_1$ 被拒绝；如果看到 Y，$H_2$ 被拒绝

### Phase D: 稳定边界映射（Stability Boundary Mapping）
- [ ] 在关键参数空间中**系统扫描**，找到稳定/不稳定边界
- [ ] 识别**最脆弱模态**（哪些参数组合最先失稳？）
- [ ] 对稳定区域进行**裕度评估**（离边界多远是安全的？）

### Phase E: 配置固化（Configuration Freeze）
- [ ] 将稳定运行的参数组合**固化**为"已知良好配置"
- [ ] 记录**已知失败模式**和对应症状（方便下次快速诊断）
- [ ] 建立**回归测试集**——每次代码或参数变更后跑一遍保证不退化

这就是系统科学在计算物理中的终极应用——让你的计算 pipeline 不只是"跑代码"，而是一个**有自我感知和自我调节能力的系统**。

## 0. 问题本质：这不是"忘了更新文件"

### 0.1 事件链重构

```text
时间线
```

### 0.2 为什么人类团队不会犯这个错，但两个 AI 会话会

| | 人类团队 | 两个 AI 会话 |
|---|---|---|
| **状态存储** | 共享记忆，会议对齐 | 各自独立的上下文窗口 |
| **更新机制** | 口头/书面通知所有成员 | 写入文件 → 对方需**重新读取**才能感知 |
| **陈旧数据风险** | 低（人会主动问"最新结论是什么"） | **高**（AI 读到旧文本即以此为真） |
| **修正传播** | "那个结论已经推翻了"——一句话 | 需要对方显式重新检索修正段落 |

```text

    │
```

## 2. 失效模式分类：这是配置管理的经典反模式

| 系统工程的 CM 原则 | 你的现状 | 差距 |
|---|---|---|
| **单一真相源（Single Source of Truth）** | 同一事实存在于 3 处：MG/log, tbplas-internals, 02_deep_dive | ❌ 三处可能不一致 |
| **变更传播（Change Propagation）** | 前方更新 log，总部文档有人类手动追加修正 | ⚠️ 半自动，不完整 |
| **配置审计（Configuration Audit）** | 无自动化检查 | ❌ 完全依赖人类/AI 主动读取 |
| **版本基线（Baseline）** | 无明确的"当前有效版本"标记 | ❌ 新旧结论同存于文档 |
| **变更通知（Change Notification）** | 无主动推送机制 | ❌ 依赖轮询 |

将上述映射到分布式系统的经典问题：

| 分布式系统概念 | 你的知识系统中的对应 |
|--------------|-------------------|
| **最终一致性 vs 强一致性** | 文档追加修正 = 最终一致性；AI 决策需要读己之写的强一致性 |
| **陈旧读取（Stale Read）** | 总部 AI 读到未被充分标记为失效的旧结论 |
| **脑裂（Split Brain）** | 两个工作区的 AI 各自持有矛盾的世界模型 |
| **变更通知缺失** | 总部 AI 不知道自己引用的知识已经过期 |
| **无心跳/存活检测** | 没有机制检测"前方是否产生了新结论" |
| **单点故障** | 前方→总部的信息传递完全依赖人类手动 |

### 方案 A：文档结构改革（最小代价，立即执行）

**原则**：失效的结论必须被**就地标记为失效**，而非仅在末尾追加修正。

**具体操作**：

(1) **在旧结论处插入失效标记**——让任何读取该段落的 AI 第一眼就看到：

```markdown

> **⚠️ 本节原始分析框架已作废 (2026-06-21)。**
> 原分析将 NaN 归因于 Chebyshev 三项递推的正交性丢失，
> 并将 rescale 作为次要因素。**0621 M 扫描实验证伪了此框架。**
> NaN 的真实原因是 `rescale` 误配（rescale=9.0 < 半带宽 ~10 eV）。

> 关于"问题 B: 基线偏移"的分析也基于 rescale=9.0 的旧数据，
> **应使用 rescale=-1 的数据重新评估。**

```

(2) **建立"结论状态表"**放在文档头部：

```markdown

|------|:---:|---------|---------|
```

## QA-004: plan-task-run 工作流退化 — 开环控制在非线性环境中的失效

### 用户问题（原文）

> 回顾 /home/wyl/project/MG 的开发过程，docs 下有多个 plan, task, log。预期的工作流是先建立 plan 的计划，根据这个计划建立 tasks 的任务，再逐个执行任务并记录到 log 中。但在实际的开发过程中，往往遇到各种各样在编写 plan 时没有预计到的阻塞，或是在与其他项目的协作中需要临时增加功能。以计算电导为例，在 docs 下新建了一个 sigma 子目录，用于盛放电导计算相关的文档，并在这个子目录下新建了 plan 和 task。但此前提到的关于 graphene QHE 问题出现了，又再次新建了 M_scan_test_plan.md, M_scan_test_task.md, baseline_shift_plan.md 等文件。一开始预计的 plan-task-run 的工作流名存实亡，几乎不再看最初的 plan 文件，而是在最新的修改完成后使用 sync-docs 做事后修补。问题出在了哪里？

### 回答：诊断 + 审计 + 建议

---

## 0. 根因诊断：开环控制 vs 非线性现实

### 0.1 你的预期（开环预设）

```text
plan.md ──→ tasks.md ──→ 执行 ──→ log.md
  │            │           │
  └── 预设路径   └── 拆解步骤  └── 记录结果
```

隐含假设：**plan 编写时已知的信息足以覆盖整个执行过程**。即假设项目是一个线性系统。

### 0.2 实际发生（非线性扰动 + 无反馈修正）

```text
plan.md (总计划: 多层石墨烯 QHE)
  │
  ├─→ sigma/plan.md (子计划: ABC trilayer QHE)
  │     │
  │     ├─→ [阻塞] NaN 问题 → M_scan_test_plan.md (临时plan)
  │     │     └─→ [发现] rescale 根因 → baseline_shift_plan.md (又一plan)
  │     │
  │     ├─→ [偏离] sigma/plan.md 写的是 ABC trilayer，
  │     │     但实际先做了大量 monolayer 测试 (29 YAML)
  │     │
  │     └─→ [矛盾] M_scan_test_plan.md §1.1 仍写
  │           "M≥1024 全 NaN 崩溃区"
  │           但 log AI:0621_0324 已证实 M=1024 NaN=0
  │
  └─→ docs/plan.md 对 sigma/ 子目录零引用
       → 原 plan 已与现实脱节
       → 放弃阅读 → sync-docs 事后修补
```

每一次意外发现（NaN 根因、monolayer 先行的必要、M=1024 不 NaN）都是对原 plan 的**扰动**。你的反应是：为每个扰动创建一个新的独立 plan 文件，而不是**更新原 plan 以吸收新信息**。

这相当于：飞行计划说要直飞北京 → 遇雷暴不更新飞行计划，写新纸条"绕行 A" → 遇侧风再写"修正 B" → 最后不看飞行计划只看最近纸条 → 落地后找地勤补日志。

### 0.3 控制论视角

```
plan.md 的正确角色: 状态估计 x̂(t) — "基于目前所知，项目状态的最佳估计"
plan.md 的当前角色: 预设轨迹 x_ref(t) — "我要按这个路线走"

当新观测 y(t) [实验结果] 与 x̂(t) 不一致时:
  ❌ 当前做法: x̂(t) 不变，另建临时文件
  ✅ 应该做的: x̂(t) ← Kalman 更新 (用观测修正估计)
```

sync-docs 能做的是"文档 ↔ 代码"的对账（语法层一致），但它不能解决"plan ↔ 现实"的对账（语义层一致）。

## 4. 总结

你遇到的不是一个"计划做得不够详细"的问题——sigma/plan.md 已经非常详细了。你遇到的是**"计划没有被当作活文档来维护"**的问题。

| 问题层面 | 表现 | 根因 | 修复 |
|---------|------|------|------|
| 计划层 | 5 个 plan 文件，无人知道哪个是"当前真相" | plan 是静态预设，不是动态状态估计 | plan 状态机 + 父指针 |
| 执行层 | 实际路径 (monolayer 先行) 与 plan 路径 (ABC trilayer 直达) 偏离 | 偏离发生后未回写 plan | "实际执行路径"节 |
| 认知层 | AI 读取 M_scan_test_plan.md 时被旧数据误导 | 已证伪内容未被就地标记 | 就地 SUPERSEDED 标记 |
| 工具层 | sync-docs 只做代码↔文档对账，不做 plan↔现实对账 | 工具定位限制 | debug-workflow Phase 4 扩展 |

**核心教训**：plan 和代码一样有生命周期。代码需要重构以保持可维护性，plan 需要修订以保持与现实的同步。把 plan 当作一次性的"项目启动文档"而不是持续的"项目状态估计"，是 plan-task-run 工作流失效的根本原因。

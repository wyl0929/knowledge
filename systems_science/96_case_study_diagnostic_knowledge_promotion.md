## 摘要

在 MG 项目 R04 Phase D 的 LDOS 诊断中，三个 Chebyshev KPM 变体（TBPM ts=20001、ts=4096、cpu）对 LL 峰位给出了一致的读数（ΔE < 5 meV）——初看是完美的交叉验证。但第四个方法 Haydock（Lanczos 递归，不经过 Chebyshev 多项式）给出了系统性偏移 +50–70 meV 的峰位。三方法的一致不是验证，是回声——它们共享 Chebyshev 框架，共享同一个潜在的故障模式。

这个发现触发了对诊断信息上传机制的重新审视。此前的工作流将诊断结论从 Execution（前线）传递到 Planning（总部）再到 shared/ 和 knowledge/ 的过程建模为**等增益传输**——观测数据和因果推论以相同的确定性在知识递阶中流动。但 R04 的诊断经验表明，测量事实（「Haydock 峰位 0.830 eV，TBPM 峰位 0.762 eV，差 68 meV」）和因果推论（「TBPM 存在系统性偏差」）是两种**不同增益的信息**。前者是传感器输出，确定性极高，应自由流向高层级；后者是观测器归因，确定性取决于独立来源的数量和独立性质量，应受到增益衰减。

本文提出一个**三层增益控制协议**，将诊断产出按确定性分为事实（fact）、推论（interpretation）、建议（recommendation），分别赋予高、低、极低增益，并定义各层级的晋升门禁条件。核心判据——「两个来源是否功能独立」——被形式化为**共享故障模式检验**：两个方法不能共享任何一个可能出错的组件。该判据同时解释了科学诊断（Chebyshev vs Lanczos）和政治治理（地方检测 vs 跨行政区检测）中「假一致」现象的根源。

## 1. 问题背景：三等增益的传输是一等增益的传输

### 1.1 诊断产出的三种声明

一次诊断实验产出不是单一的信息块。它包含三个不同确定性的声明层：

| 声明类型 | 确定性 | 例（D.1g Haydock 对比） | 会被推翻吗？ |
|------|:---:|------|:---:|
| **事实 (fact)** | ~99% |「Haydock LDOS 峰位 0.830 eV，TBPM 峰位 0.762 eV，差值 68 meV」| ❌ 不会。这是测量结果，可复现。 |
| **推论 (interpretation)** | ~50%（方向未确认） |「TBPM Chebyshev LDOS 峰位相对于 Lanczos 方法存在系统性偏低」| ⚠️ 可能。Haydock 也可能是错的那一方。 |
| **建议 (recommendation)** | ~25%（建立在未确认推论上） |「不应用 TBPM LDOS 峰位做 LL 拟合」| ⚠️ 如果推论方向反了，建议就反了。 |

### 1.2 此前工作流中的传输模型

在 debug-workflow v2.0 的 Phase 4B 晋升机制中，知识从 L3（项目 log）→ L2（shared/）→ L1（knowledge/）的晋升被建模为二值判断——是否经过独立实验交叉验证。这是一个**等增益模型**：一旦验证通过，整条结论以相同的确定性向上传播。

```
等增益模型（旧）:
  诊断结论 ──→ L3 log.md
  交叉验证通过？──Yes──→ L2 shared/  ← 整条结论原样晋升
                  ──No───→ 留在 L3
```

这个模型在处理 Hall 基线偏移（案例 #1）时已经暴露了问题：VBL 的「条件收敛+浮点随机游走」结论被一个实验（改变 M 观察偏移量）"验证"后，整条写入了 shared/。但验证实验与被诊断对象共享 Chebyshev 框架和 Nyquist 混叠缺陷——所谓的验证只是回声。

### 1.3 R04 Phase D 的触发事件

D.1d 用三种 Chebyshev 变体验证 LL 峰位——ts=20001、ts=4096、cpu——三者给出完全一致的峰位（ΔE < 5 meV）。按旧模型的判据，这已是完美的交叉验证，结论应晋升 L2。

但 D.1g 用 Haydock（Lanczos 递归，不经过 Chebyshev 多项式）重复了同样的测量——峰位系统性偏移 +50–70 meV。三方法的一致被证明是回声而非验证。

**核心洞察**：不是验证实验的数量不够，是验证实验的独立性不够。三个实验共享同一个故障模式（Chebyshev 三项递推），它们的一致恰恰是共享故障的证据。

## 2. 系统建模：传感器、观测器与增益控制器

### 2.1 诊断系统作为信息处理管道

将一次诊断实验建模为三级信息处理管道：

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   传感器      │     │   观测器      │     │   执行器      │
│  (测量)       │ ──→ │  (归因)       │ ──→ │  (响应)       │
│              │     │              │     │              │
│ Haydock=0.830│     │「TBPM 偏了」  │     │ 弃用 TBPM    │
│ TBPM  =0.762│     │              │     │ 改用 Haydock │
│              │     │              │     │              │
│ 确定性: 99%  │     │ 确定性: 50%   │     │ 确定性: 25%  │
│ 增益: 高     │     │ 增益: 低      │     │ 增益: 极低   │
└──────────────┘     └──────────────┘     └──────────────┘
```

**传感器**是测量设备（计算代码），输出纯观测数据。它几乎不会出错——如果代码逻辑正确，输出就是输出。**观测器**是人类（或 AI）对观测数据做因果归因。它经常出错——因为同一组观测数据可以对应多个因果模型。**执行器**基于归因采取行动，它的正确性完全依赖于观测器的准确性。

传感器不撒谎，观测器会。旧晋升模型的根本缺陷是：它把传感器和观测器的输出打包成同一条「结论」，以相同增益传输。

### 2.2 增益控制的工程含义

增益控制就是**对不同确定性的信号施加不同的放大倍数**：

$$\text{输出} = G_{\text{fact}} \cdot \text{事实} + G_{\text{interp}} \cdot \text{推论} + G_{\text{recomm}} \cdot \text{建议}$$

其中 $G_{\text{fact}} \approx 1.0$（无衰减），$G_{\text{interp}} \approx 0.3$（强衰减），$G_{\text{recomm}} \approx 0.1$（极强衰减）。

这里的「输出」不是电信号，而是**信息在知识递阶中向上传播的距离**。高增益信息可以自由穿越 L3 → L2 → L1 的门禁；低增益信息被限制在 L3 内，等待独立验证以提升其增益。

| 信息类型 | 增益 | L3 (项目内) | L2 (跨项目 shared/) | L1 (领域 knowledge/) |
|------|:---:|:---:|:---:|:---:|
| 事实 | 高 | ✅ 立即 | ✅ 立即 | ⏸️ 积累为案例素材 |
| 推论 | 低 | ✅ 标注 NEEDS_VERIFICATION | ⚠️ 等独立来源确认方向后 | ❌ 不单独写入 |
| 建议 | 极低 | ✅ 措辞「暂不推荐」 | ⚠️ 等推论晋升 L2 后 | ❌ 不单独写入 |

## 3. 独立来源的形式判据：共享故障模式检验

### 3.1 从名义独立到功能独立

两个方法是否构成独立来源，不是看它们名义上是否不同，而是看它们是否会因为同一个原因同时出错。

**共享故障模式检验**：
1. 列出两个方法各自依赖的组件链
2. 找出两个组件链的交集
3. 如果交集非空，两个方法**不是**功能独立的——它们在共享故障模式下会同时失效

### 3.2 检验实例

| 方法对 | 共享组件 | 功能独立？ | 一致意味着？ |
|------|------|:---:|------|
| TBPM ts=20001 ↔ TBPM ts=4096 | Chebyshev 三项递推 `p2=2*H*p1-p0` | ❌ | 回声——不是验证 |
| TBPM ts=20001 ↔ TBPM cpu | Chebyshev 三项递推 | ❌ | 回声 |
| TBPM (Chebyshev) ↔ Haydock (Lanczos) | 无——完全不同的算法框架 | ✅ | 如果一致 → 强验证；如果不一致 → 需要第三种方法破局 |
| 天水市疾控 ↔ 天水市二院 | 地方行政压力 | ❌ | 回声（两者都给出了 ~27 μg/L） |
| 天水本地检测 ↔ 西安市中心医院 | 无——跨行政区 | ✅ | 如果不一致 → 至少一方有问题（528 vs 27 μg/L） |

### 3.3 检验的实践规则

设计诊断实验时，不要在同一个算法框架内换参数——你只是在收集回声。改换算法框架。不要问「还能怎么调参数」，要问「如果核心假设 X 是错的，什么方法仍然能给出正确答案」。

## 4. 协议设计：诊断 Phase 的信息回传方案

### 4.1 诊断产出的结构化模板

诊断 Phase 完成后，Execution 会话在 tasks.md 中记录结论时，强制使用三层分离格式：

```markdown
### 任务 D.X: [诊断名称] ✅

**观测** (fact, 确定性 ~99%):
- [纯测量数据，无归因]
- 例: Haydock site0 峰位 0.830 eV; TBPM site0 峰位 0.762 eV; ΔE = 68 meV

**推论** (interpretation, 确定性取决于独立来源):
- [因果归因，标注方向确认状态]
- 例: → Chebyshev LDOS 峰位相对于 Lanczos 方法系统偏低
  → 方向待确认: 需第三种独立方法破局
  → 独立来源: D.1d (Chebyshev 变体间一致, 仅 1 个独立来源), D.1g (Lanczos, 第 2 个独立来源), D.1h 待执行

**建议** (recommendation, 仅在推论确认后给出):
- [行动指南，标注适用范围]
- 例: → 暂不推荐用 TBPM LDOS 峰位直接做 LL 拟合
  → 适用范围: B≠0 TBPM LDOS in trilayer graphene
```

### 4.2 三层增益控制的晋升门禁

```
事实 (观测数据, 确定 ~99%)
  ├── 晋升 L2 条件: 可复现 (至少一次独立重复给出相同读数)
  └── 晋升 L1 条件: 积累为案例素材 (至少一个完整叙事弧线)

推论 (因果归因)
  ├── 留在 L3 条件: 默认 — 标注 NEEDS_VERIFICATION
  ├── 晋升 L2 条件: 至少 2 个功能独立的方法指向同一方向
  │   └── 独立来源判定: 通过共享故障模式检验
  └── 晋升 L1 条件: 推论已晋升 L2 + 形成完整叙事弧线 (问题→诊断→确认→教训)

建议 (行动指南)
  ├── 留在 L3 条件: 默认 — 措辞「暂不推荐」「实验性」
  ├── 晋升 L2 条件: 推论已晋升 L2 + 适用边界明确标注
  └── 晋升 L1 条件: 不建议 — 建议太依赖具体工具版本, 不适合作为领域通用知识
```

### 4.3 批量 vs 实时晋升

不是每条诊断结论都需要立即晋升。推荐按诊断线批量处理：

```
诊断线完成 (如 D.1b-D.1h 全部结束):
  1. Execution 在 tasks.md 中按三层模板写好观测/推论/建议
  2. Execution 在 STATUS 中写汇总交接条 → Planning 处理
  3. Planning 读取 tasks.md 中的三层结论:
     a. 事实部分 → 立即写入 plan.md「已知限制」+ L2 shared/
     b. 推论部分 → 写入 plan.md「已知限制」, 标注 NEEDS_VERIFICATION
     c. 建议部分 → 写入 plan.md, 措辞「暂不推荐」
  4. 等独立验证完成 → Planning 更新推论增益 → 晋升 L2
  5. 等完整叙事形成 → Planning 写入 L1 案例
```

### 4.4 反例检查：VBL 结论为什么违反协议

| 步骤 | VBL 实际做的 | 按协议应该做 |
|------|------|------|
| 观测记录 | ✅ 正确：σ_xy 偏移量数据记录完整 | — |
| 推论归因 | ❌ 未标注 NEEDS_VERIFICATION | 应标注「方向待确认：Nyquist 混叠作为替代解释未被排除」 |
| 独立来源 | ❌ 0 个：只用了改变 M 一个独立来源；改变 M 和改变 rescale 共享 Chebyshev 框架 | 应引入非 KPM 方法（如 quantum-kite）作为独立来源 |
| 晋升 L2 | ❌ 推论以高增益写入 shared/ | 推论应留在 L3, 仅事实（偏移量数据）写入 L2 |
| 后果 | 错误推论在 shared/ 中存留数周, 成为后续决策依据 | — |

## 6. 核心教训

### 6.1 理论教训

1. **信息有增益属性**。不是所有「结论」都是等价的——观测数据和因果归因是两种不同确定性的信号，应该以不同的增益在系统中传播。将它们打包成同一条「结论」是等增益模型的根本缺陷。

2. **独立不是名义属性，是功能属性**。两个方法是否独立不取决于它们叫什么名字，而取决于它们是否共享任何一个可能出错的组件。共享故障模式检验提供了可操作的工程判据。

3. **传感器和观测器的分工是诊断系统设计的第一原则**。传感器负责测量（高确定性），观测器负责归因（低确定性）。信任传感器，验证观测器。任何将两者捆绑传输的协议都会在观测器出错时将错误放大到整个知识系统。

### 6.2 实践教训

1. **诊断结论必须按三层模板结构化**：观测（事实）、推论（归因）、建议（行动），分别标注确定性和独立来源。

2. **推论晋升 L2 的门禁不是「是否验证过」，而是「是否有至少两个功能独立的来源指向同一方向」**。一个来源的多次重复不是验证。

3. **晋升时机不是每条结论独立决定，而是按诊断线批量处理**。一条诊断线的完整叙事本身就是第三层信息——它不仅包含事实和推论，还包含「我们如何发现这个推论」的方法论价值。

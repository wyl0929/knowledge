# 案例研究: 关闭报告作为状态检查点 — 研究管线中的信息耗散与可恢复性

> **领域标签**: 系统科学 · 控制论 · 信息论 · 知识管理 · 研究工作流
> **时间跨度**: 2026-05 ~ 2026-08（石墨烯项目群全生命周期）
> **相关项目**: `/home/wyl/project/MG/`, `DW/`, `TBG/`, `TMBG/`, `TDBG/`
> **关联案例**:
>   - `93_case_study_problem_response_workflow.md` — 偏差升级协议（本案例解决的是"无偏差时"的信息保存问题——正常关闭与阻塞关闭）
>   - `95_case_study_session_handoff.md` — 会话交接（关闭报告是 Phase 级别而非会话级别的交接）
>   - `96_case_study_diagnostic_knowledge_promotion.md` — 信息增益控制（关闭报告的三层声明：事实/推论/建议的分离保存）
> **核心协议**: 无现有协议——本文档提议新协议「Phase 关闭报告」
> **关键数据**: DW `data/tbpm/Lm_4/`, `Lm_10/`（无文档），MG `data/phase3X/README.md`（唯一反例）

## 摘要

2026 年 8 月，用户在对石墨烯项目群（MG/DW/TBG/TMBG/TDBG）进行回顾时发现：DW 项目在停滞仅 2 个月后，其数据目录（`data/tbpm/Lm_4/`、`Lm_10/`）中的几十个输出文件已完全不可理解——参数含义、计算目标、与论文的对应关系全部丢失。对比之下，MG 项目的 `data/phase3X/README.md` 是唯一的反例——一份简洁的数据索引使得该 Phase 的成果在数周后仍可快速恢复。

本文从控制论和信息论的视角出发，将研究管线建模为**开放耗散系统**：每一次计算产生信息，每一次上下文切换（项目间跳转、长时间停顿）导致信息不可逆地耗散。**关闭报告**的本质是**状态检查点**——在 Phase 终止（完成/阻塞/废弃）时，将系统的高维运行状态压缩为一份低维但可恢复的摘要，使得未来任意时刻的观测者能重建足够的上下文以继续工作。

本文分析了石墨烯项目群中五类信息耗散模式，提出关闭报告的**最小状态向量**（八项必含信息），并从可观测性、可恢复性、信息压缩比三个控制论概念论证每一项的设计必要性。最后，给出与现有 plan→task→log 文档体系的集成方案和模板。

> **核心论点**：研究管线中的信息遗忘不是记忆力的失败，而是**系统设计缺陷**——现有流程只有"启动"（plan）和"运行"（task/log），没有"关闭"（wrap-up）。这等价于一个只有开机和运行、没有关机和存档的操作系统。

## 1. 问题建模：研究管线作为开放耗散系统

### 1.1 信息产生与耗散的动力学

将单个研究 Phase 建模为一个动力学系统：

```
┌─────────────────────────────────────────────────────┐
│                 Phase 系统边界                        │
│                                                     │
│  输入 u(t)          状态 x(t)          输出 y(t)     │
│  ─────────         ─────────         ─────────     │
│  · 参数配置    →    · 当前理解    →    · 数据文件     │
│  · 文献输入         · 代码版本         · 图表         │
│  · 计算资源         · 中间结果         · 日志条目     │
│                     · 参数记忆                       │
│                     · 上下文关联                     │
│                                                     │
│  耗散项: γ·x(t) —— 随时间指数衰减                    │
└─────────────────────────────────────────────────────┘
```

系统的状态向量 $x(t)$ 包含研究者在时刻 $t$ 对该 Phase 的全部可操作知识——参数选择的理由、数据的物理含义、中间结论、已知限制。这个状态的衰减由两个机制驱动：

1. **记忆衰减**（人脑）：$dx/dt = -\gamma_h \cdot x$，$\gamma_h$ 是人类遗忘速率。DW 项目 2 个月后的状态恢复率接近于零。
2. **上下文切换损耗**（注意力）：每次切换到另一个项目，当前项目的状态被"换出"工作记忆，重新加载的代价 $\propto$ 状态规模。

关键洞察：**log.md 记录的是输出 $y(t)$（发生了什么），不是状态 $x(t)$（现在知道什么）。** 从 log 恢复到状态需要反向推断——一个信息论上不可逆的操作。

### 1.2 为什么 log 不足以恢复状态

以 DW 项目为例：

| 信息需求 | log 中有吗？ | 能从 log 推断吗？ |
|----------|:----------:|:---------------:|
| Lm_4 和 Lm_10 是什么意思？ | ❌ | ❌ 无法推断 |
| 这些 QE 热力图中哪张是"最终版"？ | ❌ | ❌ 无法推断 |
| 使用的 TBPM 参数（m, rs, ts）是多少？ | ⚠️ 部分 | 🟡 需要追溯多天前的配置 |
| 计算结论是什么？"成功"还是"失败"？ | ❌ | 🔴 log 记录操作，不记录判断 |
| 为什么这个方向停了？还值得继续吗？ | ❌ | ❌ 完全不可知 |

log 记录的是**微分** $dy/dt$（每次操作），状态 $x(t)$ 需要对微分的历史积分才能得到——但积分常数（初始状态和中间判断）没有被记录。这就是为什么从 log 重建状态在信息论上不可行。

### 1.3 现有文档体系中缺失的环节

```
现有流程:
  plan.md ──→ tasks.md ──→ log.md ──→ ??? (信息在此处耗散)

应有流程:
  plan.md ──→ tasks.md ──→ log.md ──→ WRAPUP.md (状态保存)
                                          │
                                          ▼
                                  可恢复的长期记忆
```

从控制论角度，这是**开环控制**（open-loop）和**闭环控制**（closed-loop）的区别。没有关闭报告的系统是开环的——执行完后不反馈状态到长期存储。关闭报告闭合了这个回路。

## 2. 五类信息耗散模式（石墨烯项目群实证）

对五个石墨烯项目的审计识别出五种不同的耗散模式：

### 模式 A：数据无索引（DW — 最严重）

**实例**: `DW/data/tbpm/Lm_4/` 和 `Lm_10/` 目录包含数十个 `.txt`、`.npz`、`.png` 文件，无任何 README 或索引。

**耗散机制**: 文件系统只保留数据，不保留数据的**生成条件**和**物理含义**。文件名（如 `qe_LSW_AC_E14_top.png`）携带了部分信息（AC 畴壁、第 14 个能量窗口、顶层），但缺失：
- 这是什么计算？（TBPM QE，但参数是什么？）
- Lm_4 vs Lm_10 的区别？（畴壁宽度 $l_m$ 的两个取值？但具体值是多少？）
- 哪些是最终结果，哪些是中间测试？
- 结论是什么？

**控制论诊断**: **可观测性矩阵秩不足**——从输出（文件列表）无法唯一重建系统状态。

### 模式 B：数据与文档物理分离（TBG — 数据失踪）

**实例**: `TBG/runs/` 目录完全为空，但 `docs/log.md` 记录了大量的 LDOS 计算和带隙分析。

**耗散机制**: 数据可能在集群上未被回传，但没有任何文档记录这一点。STATUS.md 声称"数据一致性 95%"，但本地无任何数据可验证。

**控制论诊断**: **传感器断开**——文档声称观测到了输出（数据存在），但信号链路（集群 → 本地 scp → runs/）在某个节点断开，且断开本身未被记录。

### 模式 C：阻塞悬置（TMBG — 状态冻结无快照）

**实例**: TMBG 的 MPI int32 溢出阻塞自 06-14 以来未解决。`runs/0801/` 和 `0802/` 为空目录。

**耗散机制**: 阻塞发生时，研究者没有保存当前状态快照。2 个月后恢复时，需要：
- 回忆阻塞的具体技术细节（MPI_Allreduce count 超 INT_MAX）
- 判断是否已有修复方案
- 评估是否还值得修复

这三项信息在阻塞时不记录，恢复成本随时间指数增长。

**控制论诊断**: **死区时间过长**——反馈回路中断 2 个月，回路中的积分器（人类记忆）已完全放电。

### 模式 D：方向废弃无归档（TDBG — 完全信息丢失）

**实例**: TDBG 项目自 2025-07 废弃，只剩一个简陋的 README.md 和散落的 Python 脚本。

**耗散机制**: 废弃时没有"退役报告"——没有记录：
- 当初为什么开始这个方向？
- 做到了什么程度？
- 为什么放弃？
- 有没有可复用的代码或数据？
- 有没有"如果条件 X 满足可以重启"的可能？

**控制论诊断**: **无终止状态**——系统被强行断电而非正常关机，RAM 中的全部状态丢失。

### 模式 E：有索引但未制度化（MG phase3X — 唯一正面案例）

**实例**: `MG/data/phase3X/README.md` 包含：
- 数据目录映射表（语义目录 → runs/ 来源）
- 最优参数一行总结
- 内容说明

**优势**: 这份 README 证明了用户**有能力**写高质量的数据总结。问题在于这只是一个孤立的好习惯，没有被制度化为每个 Phase 的强制步骤。

**控制论诊断**: **手动检查点**——有效但不保证执行，依赖研究者记得去做。

## 3. 关闭报告的设计规范

### 3.1 设计目标（从控制论导出）

| 目标 | 控制论概念 | 含义 |
|------|----------|------|
| **可恢复性** | 可观测性 | 未来任意时刻，仅凭关闭报告 + 数据目录就能重建足够上下文 |
| **可决策性** | 可控性 | 报告必须包含足够信息让未来自己判断"是否重启、如何重启" |
| **最小性** | 信息压缩 | 用最少的信息量达到可恢复性，降低书写成本和阅读成本 |
| **可审计性** | 可追溯性 | 报告的每项声称都能追溯到 log 或数据文件中的证据 |

### 3.2 最小状态向量：八项必含信息

从信息论角度，一个 Phase 关闭报告需要保存的**最小状态向量**包含八个分量：

---

#### ① 目标陈述（设定点）

**内容**: Phase 要回答的科学问题或要达成的工程目标，一句话。

**为什么必要**: 目标是反馈控制的参考信号。没有目标记录，未来无法判断 Phase 是"成功"还是"失败"——因为不知道成功的定义。

**反例**: DW `data/tbpm/Lm_4/` 中没有目标陈述 → 无法判断这些 QE 热力图是"达到了预期"还是"发现有问题所以放弃了"。

**要求**: ≤ 3 句话。引用 plan.md 中详细目标。

---

#### ② 终止状态（闭环信号）

**内容**: 以下四选一，附一句话理由：
- ✅ **完成 (DONE)**: 目标达成，产出合格
- 🟡 **阻塞 (BLOCKED)**: 遇到无法解决的障碍，暂停
- 🔴 **证伪 (DISPROVED)**: 核心假设被推翻，方向不可行
- ⚫ **废弃 (ABANDONED)**: 非技术原因终止（优先级变化、资源转移等）

**为什么必要**: 这是整个关闭报告最重要的一个字段。它决定了未来自己面对这个 Phase 时的**第一反应**——是"太好了，可以直接用"还是"这条路走不通，别重蹈覆辙"。

**反例**: TMBG MPI 溢出阻塞没有终止状态标记 → "到底还能不能做？" DW "n183 DW QE 计算, slm_id 278490" 状态不明。

**要求**: 四个状态之一 + 一句话理由。阻塞状态必须附阻塞诊断结论。

---

#### ③ 最终参数（控制输入快照）

**内容**: 产生最终/最优结果的那组参数。格式：`参数名 = 值`，一行一个。物理含义简要说明。

**为什么必要**: 参数是控制输入 $u(t)$。未来要复现结果或在此基础上改进，参数是必需的初始条件。

**反例**: DW Lm_4 vs Lm_10 的 `l_m` 具体值不可知 → 即使想继续这个方向，也无法确定起点。

**要求**:
- 不超过 10 行
- 包含所有非默认参数
- 标注哪个是"最优"或"最终采用"
- 引用对应的 YAML 配置文件路径

---

#### ④ 数据清单（输出快照）

**内容**: 表格，每行列一个数据产物。列：`语义描述 | 文件路径 | 格式 | 是否最终版`。

**为什么必要**: 数据是输出 $y(t)$。Phase 关闭几周后，`runs/MMDD/` 下有几百个文件，未来自己不可能逐个打开判断哪些有用。

**反例**: DW `data/tbpm/Lm_4/` 中 40+ 个 QE PNG 和一个 `.npz` → 不知道哪些是最终版、哪些是中间测试。

**要求**:
- 表格形式
- 覆盖所有关键输出
- "最终版"文件明确标注，其余标"中间"或"废弃"
- 引用具体文件路径（非目录）

---

#### ⑤ 关键发现（状态变量的语义摘要）

**内容**: 不超过 5 条的 bullet list，每条一句话。只写**结论性**发现，不写过程。

**为什么必要**: 这是状态 $x(t)$ 中"理解"部分的压缩。log 记录了过程（"做了什么"），关键发现记录结果（"知道了什么"）。

**反例**: MG VBL Phase A–M 的 11 个 Phase 在 log 中有详细记录，但如果要回答"所以到底学到了什么？"需要读完几十页 log 才能总结。关闭报告一句话解决：**"根因是 Nyquist 混叠，不是浮点精度；int ≥ M 即可消除。"**

**要求**:
- 粒度：一句话可独立理解
- 区分事实发现（✅）与待验证推论（⚠️）
- 与被证伪的假设分开写（证伪也是发现）

---

#### ⑥ 被证伪的假设（负面知识）

**内容**: "我们证明了 X 不是原因 / Y 方法不适用于此问题"。一行一个。

**为什么必要**: 负面知识（证伪）在科学中至少和正面知识同样有价值，但极容易被遗忘。6 个月后，如果记忆模糊，很容易把已证伪的假设当作新想法重新尝试——这是**重复浪费**的根源。

**反例**: MG `docs/archive/` 中有 17 个归档文档，但没有一个汇总了"哪些东西被证明是死路"。你的 memory `kubo-bastin-convergence.md` 做了这个（quad precision → ❌ 已证伪），但这是特例而非制度。

**要求**:
- 每条标记 ❌
- 附一句话证伪依据
- 对阻塞状态尤为重要——记录"尝试过但失败的解决方案"

---

#### ⑦ 遗留问题与重启条件（开环信号）

**内容**:
- 未解决的技术问题列表
- 对每个问题：**重启条件**（"当 X 发生时，可以重新考虑"或"需要先解决 Y 才能继续"）

**为什么必要**: 这是 Phase 之间的**反馈耦合**。一个 Phase 的遗留问题可能是另一个 Phase 的前置条件。不记录这些耦合关系，项目群退化为孤立的、无优先级的任务集合。

**反例**: TMBG MPI 溢出阻塞没有任何"重启条件"——是等 tbplas 修复 MPI_Count？还是改用更小的体系绕过去？这两种不同的重启条件对应完全不同的等待策略。

**要求**:
- 每个遗留问题标注严重性（🔴 阻塞 / 🟡 待验证 / 🔵 改进）
- 每个阻塞问题必须有重启条件
- 引用相关 plan 或其他 Phase 的依赖关系

---

#### ⑧ 元数据

**内容**: Phase 名称、日期、执行者（人/AI）、父 plan 引用。

**为什么必要**: 可追溯性。未来需要在 plan.md 或 blue_print.md 中定位完整上下文。

**要求**: 固定格式，≤ 5 行。

---

### 3.3 为什么这八项是最小充分集

从信息论角度论证：关闭报告的目标是将高维系统状态 $x \in \mathbb{R}^N$（$N$ 很大，包含所有代码细节、参数尝试、中间结果、研究者脑中的判断）压缩为低维摘要 $s \in \mathbb{R}^8$（八项必含信息），使得未来观测者可以：

1. **判断**（不需要重新计算就能回答）：
   - 这个 Phase 成功了吗？（→ ② 终止状态）
   - 我该用它还是避开它？（→ ② + ⑥）
   - 值得重启吗？（→ ⑦ 重启条件）

2. **复现**（需要重新计算，但知道精确的起点）：
   - 用的什么参数？（→ ③ 最终参数）
   - 数据在哪？（→ ④ 数据清单）
   - 目标是什么？（→ ① 目标陈述）

3. **学习**（不需要重新计算，可以站在肩膀上）：
   - 学到了什么？（→ ⑤ 关键发现）
   - 什么行不通？（→ ⑥ 被证伪的假设）

这八项构成了**可恢复性充分统计量**——给定这八项，恢复完整上下文的信息缺口最小；缺少任何一项，恢复成本至少翻倍。

## 4. 与现有文档体系的集成

### 4.1 存放位置

关闭报告应放在**数据旁边**，而非 docs 目录下：

```
Phase 目录/
├── plan.md          ← 目标/方法（Phase 开始前写）
├── tasks.md         ← 任务分解（Phase 开始前写）
├── log.md           ← 操作记录（Phase 执行中写）
├── WRAPUP.md        ← 🆕 关闭报告（Phase 结束时写）
└── data/            ← 或 runs/MMDD/
    └── README.md    ← 🆕 数据索引（可合并到 WRAPUP 中）
```

**理由**: 未来自己浏览 `data/` 目录时，关闭报告和数据在同一个视图中。如果放在 `docs/` 下，需要额外的"记得去 docs/ 找"的步骤——增加摩擦。

对于 MG 这种使用 `phase_{ID}_{slug}/` 子目录结构的项目，`WRAPUP.md` 直接放在 phase 目录下。

### 4.2 触发时机

| 触发条件 | 动作 |
|----------|------|
| Phase 所有 tasks 标记 [x] | 写 DONE 关闭报告 |
| 阻塞持续 > 1 周且无进展 | 写 BLOCKED 关闭报告 |
| 核心假设被实验推翻 | 写 DISPROVED 关闭报告 |
| 项目优先级调整，Phase 被砍 | 写 ABANDONED 关闭报告 |
| 在项目间切换前（暂停一个项目去做另一个） | 写**当前 Phase 的轻量检查点**（至少 ①+②+③+④） |

最后一个触发条件是最容易被忽略但最重要的。DW → TBG → TMBG → MG 的每次跳跃，都应该在跳走前花 10 分钟写一个轻量关闭报告。

## 6. 更深的控制论洞察：研究管线作为多层记忆系统

### 6.1 五层记忆递阶

将研究管线中的信息存储建模为五层递阶记忆系统（类似计算机的存储层次）：

| 层级 | 存储介质 | 容量 | 持久性 | 访问延迟 | 示例 |
|:----:|------|:----:|:----:|:----:|------|
| L0 | 人脑工作记忆 | ~4-7 chunks | 秒-分 | 0 | 当前正在想的参数 |
| L1 | 人脑长期记忆 | 大但不可靠 | 天-月（衰减） | 秒 | "我记得做过类似的计算" |
| L2 | 会话级文档（log.md） | 大 | 月-年 | 分钟 | "让我翻一下 log..." |
| L3 | Phase 级文档（plan+WRAPUP） | 中 | 年 | 分钟 | "这个 Phase 的结论是什么" |
| L4 | 项目级文档（CONTEXT/STATUS） | 小（摘要） | 年 | 分钟 | "这个项目整体在做什么" |
| L5 | 跨项目知识（memory/shared/） | 中 | 年+ | 分钟 | "Kubo-Bastin 的 M 不要超过 2560" |

**关闭报告解决的是 L1 → L3 的断层。** 当前系统中，L0/L1 的信息在上下文切换时丢失，L2（log）太细粒度无法快速恢复状态。关闭报告充当 L3 层的**检查点**——将 L0/L1 中的关键状态压缩保存到持久存储。

### 6.2 为什么 10 分钟的投资值得

控制论中有一个概念叫**重启成本**（restart cost）——系统从中断状态恢复到正常运行状态所需的资源。对于研究管线：

$$\text{重启成本} = \alpha \cdot e^{\gamma \cdot \Delta t} \cdot |x(t)|$$

其中 $\Delta t$ 是中断时长，$\gamma$ 是遗忘速率，$|x(t)|$ 是状态复杂度。关闭报告将有效状态复杂度从 $|x(t)|$ 压缩到 $|s| \ll |x(t)|$，使得重启成本从指数增长降为常数。

## 7. 实施建议

### 7.1 立即行动（零成本）

1. **为 MG 当前活跃 Phase（R04）建一个 WRAPUP 草稿**——即使是半空的，也比没有好。随着 Phase 推进逐步填充。
2. **为 DW 写一个"追溯关闭报告"**——虽然已经过了 2 个月，但从 CONTEXT/STATUS/log 中仍能还原部分状态。标记大量 `NEEDS_VERIFICATION`，但至少提供一个起点。

### 7.2 制度化（需要修改 SKILL）

1. **修改 `create-plan` SKILL**: plan.md 模板增加"关闭条件"段。
2. **修改 `run-task` SKILL**: 所有 tasks 标记完成后，输出 `WRAPUP.md` 模板并提示填写。
3. **修改 `sync-docs` SKILL**: 新增检查项——Phase 结束后是否有关闭报告。
4. **在 `create-blueprint` 中记录**: 每个 Phase 在 blue_print 中的条目增加 `wrapup` 列，链接到关闭报告。

### 7.3 最低可行版本（如果时间极其有限）

如果写完整的八项关闭报告仍然太重，**最少最少**要写这三项：

> **② 终止状态** (一句话) + **③ 最终参数** (一个 YAML 路径) + **④ 数据清单** (一个表格，至少标注哪些是最终版)

这三项可以防止最严重的信息耗散（数据不可理解）。其余五项是"锦上添花"——让恢复更高效，但不写也不会导致永久丢失。

## 8. 结论

从控制论的视角看，**关闭报告不是行政文书，是系统的状态检查点**。没有它，研究管线的每个 Phase 就是一个开环的、信息不可逆耗散的过程。当前石墨烯项目群的文档体系（plan→task→log）覆盖了"启动"和"运行"，但缺失了"关闭"——这等价于一个只有开机和运行、没有关机和存档的操作系统。每次强制断电（切换项目、长时间停顿），RAM 中的状态就永久丢失。

好消息是：修复成本极低。一份关闭报告 10-30 分钟，可以节省未来 3-20 倍的恢复时间。MG `data/phase3X/README.md` 证明了你有能力写这种文档。唯一的改变是把"偶尔做了"变成"每个 Phase 都做"。

**最有效的单点干预**：在 `run-task` SKILL 末尾增加一步——"此 Phase 所有任务完成，是否生成关闭报告？"
